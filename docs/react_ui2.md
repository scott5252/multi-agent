# React UI Full Jinja Removal Roadmap

Created: 2026-05-05
Last updated: 2026-05-05

This document continues `react_ui.md` after Specs 026 through 037. The goal is
to move from "React primary with Jinja retained as fallback" to "React is the
only browser UI and Jinja is removed from the system."

Use this as a prompt source. For each proposed spec, run the commands in order:

1. `/speckit.specify`
2. `/speckit.clarify`
3. `/speckit.plan`
4. `/speckit.tasks`
5. `/speckit.analyze`
6. `/speckit.implement`

Do not start by deleting templates. Full removal requires deletion-grade parity:
every route, direct link, form action, export, upload, filter, mutation,
diagnostic, error state, authorization check, audit event, redaction behavior,
and tenant-scope behavior must have React evidence before Jinja code is removed.

## Current Solution Context

The repository now has a React admin foundation and migrated React workspaces
from Specs 026 through 037:

- `/admin/app` - React admin shell and migration home.
- `/admin/app/migration` - migration hardening dashboard, parity matrix,
  retained fallback decisions, rollback plan, and validation evidence.
- `/admin/app/operations` - operations, reliability, and run debug workbench.
- `/admin/app/workflows` - workflow builder.
- `/admin/app/governance` - model provider, prompt, profile, routing, policy,
  and provenance governance.
- `/admin/app/skills` - skill registry lifecycle and governed tool readiness.
- `/admin/app/test-bench` - agent and workflow test bench.
- `/admin/app/memberships` - membership administration.
- `/admin/app/usage` - usage and cost analytics.
- `/admin/app/channels` - channel, Telegram, run status, and briefing
  preferences.

Existing Jinja routes remain available as authorized fallbacks. The next phase
must prove that React covers all remaining browser behavior, then remove:

- Jinja templates under `src/multi_agent_platform/web_admin/templates`.
- Legacy static CSS and JavaScript under `src/multi_agent_platform/web_admin/static`
  that exist only for Jinja pages.
- `Jinja2Templates`, `TemplateResponse`, and template view-model helpers that
  are no longer needed.
- Legacy admin route handlers whose only purpose is rendering a Jinja page.
- The `jinja2` dependency when no runtime path imports it.

## Definition Of Complete Jinja Removal

Jinja is considered fully removed only when all of the following are true:

1. No runtime route renders a Jinja template.
2. No production dependency on `jinja2` remains.
3. `src/multi_agent_platform/web_admin/templates` is removed or contains no
   runtime templates.
4. Legacy Jinja-only static assets are removed.
5. Old `/admin/...` and `/runs...` direct browser URLs either redirect to React
   equivalents or return documented retirement responses without leaking data.
6. React has deletion-grade parity evidence for every retired page, including
   platform admin, tenant admin, tenant user where applicable, unauthorized, and
   cross-tenant cases.
7. Auth0-shaped backend route tests and `AUTH_MODE=local_principal` browser
   Playwright evidence both pass for every protected replacement route.
8. Redaction, audit, tenant isolation, accessibility, performance, generated
   contract checks, QA docs, and rollback instructions pass after template
   deletion.

## Remaining Jinja Surface Categories To Validate

The inventory must be regenerated by the implementation specs, but the known
categories are:

- Admin shell and utility pages:
  `admin_shell/*`, `auth/local_login.html`, saved filters, unavailable/error
  pages, shell navigation fragments, and the current React app Jinja host
  `admin_react/app.html`.
- Workflow pages:
  workflow list, create, draft editor, version detail, publish gate, revision
  history, field help, graph preview, validation panel, and reference picker.
- Governance pages:
  model-skill config, provider list/detail/edit/catalog/test results, prompt
  list/detail/edit/history/preview, profile list/detail/edit/history/resolve,
  routing history, and run provenance.
- Skill pages:
  package list/detail/create/candidate/validation/version detail, tenant grant,
  available versions, installation list/detail/configure, readiness, smoke
  history, eligibility, audit timeline, stale conflict, and tool diagnostics.
- Test bench pages:
  suite list/detail/forms, case forms, run detail, assertion/result/trace/gate
  components, artifacts, and publish evidence.
- Operations and debugging pages:
  operations console, reliability controls, breakers, dead letters, run search,
  run detail, replay, usage dashboard, and usage export detail.
- Channel and people pages:
  Telegram configuration, briefing preferences, memberships, access/admin pages,
  and related diagnostics.
- User-facing run pages:
  `/runs` Web UI for start, status, timeline, approvals, results, artifacts,
  callback/subscription flows, and SSE/progress views.

```text
behavior, redaction rules, runtime version pinning, secret hygiene, object
storage boundaries, generated TypeScript contracts, Playwright evidence, QA
docs, and at least 90 percent relevant coverage.

React must consume backend-owned JSON contracts generated from Pydantic schemas.
Do not move authorization, tenant scoping, validation, credential readiness,
publish readiness, redaction, or audit decisions into browser-only logic.

Every spec must explicitly prove both Auth0-shaped principal behavior with
backend route tests and local-principal behavior with browser Playwright flows.
Every retired legacy route must preserve safe direct-link behavior through a
redirect, alias, documented gone response, or retained non-Jinja compatibility
handler.

Do not remove a Jinja template, route, helper, static asset, or dependency until
the spec's parity evidence shows that the React replacement covers every safe
user journey, denied state, mutation, export, filter, direct link, and error
path. Raw secrets, credential values, provider authorization headers, raw
prompts, raw completions, memory contents, raw run payloads, private channel
messages, raw tool payloads, raw test transcripts, full Telegram identifiers,
link tokens after creation, local filesystem paths, stack traces, and
unauthorized tenant labels must never appear in React UI, redirects, exports,
screenshots, QA artifacts, logs, or docs.
```

- Create one Spec Kit feature at a time. Do not run all specs in parallel.
- Do not delete templates in Spec 038. Inventory first.
- Treat `/admin/app/migration` as the operator-facing ledger until Spec 047
  replaces it with a React-only decommission summary.

  Jinja routes or convert them to JSON/redirect handlers.

  parameters, filters, saved-filter intent, and safe breadcrumbs.

  complete Jinja removal.

  suite prove no runtime path imports it.
- The final state should describe the browser UI as React-only, not React
  primary with Jinja fallback.
