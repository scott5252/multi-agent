# Autopilot Implement

## Overview

Use this skill to run an already prepared roadmap queue, such as
`specs/_autopilot/wizard-ui-roadmap`, through every Spec Kit phase and
validation gate without pausing after each spec. It generalizes the queue-runner
behavior from the React UI, React UI2, and Workflow Setup autopilot skills.

This is an autonomous Codex runbook, not a background daemon. Keep working
until the queue is complete, a hard stop condition occurs, or the user
redirects the work.

Do not stage, commit, push, or create pull requests while running this skill
unless the user explicitly asks for git actions.

## Required Input

Require one parameter: the roadmap directory under `specs/_autopilot`, for
example:

```text
specs/_autopilot/wizard-ui-roadmap
```

The directory must contain `queue.json`. Each queued spec must contain:

- `specify.md`
- `clarify.md`
- `plan.md`
- `tasks.md`
- `analyze.md`
- `implement.md`
- `autopilot.yml`
- `policy.yml`
- `validation.yml`
- `status.json`

## Preflight

1. Read `queue.json`, root `status.json`, every pending spec's
   `autopilot.yml`, `policy.yml`, and `validation.yml`.
2. Read `AGENTS.md`, the latest plan referenced by `AGENTS.md`, current git
   status, `.specify/feature.json`, and the active constitution.
3. Confirm the roadmap directory is inside `specs/_autopilot`.
4. Confirm `queue.json.next_spec` points at a pending spec or is `null`.
5. If `next_spec` is `null`, skip directly to final documentation and
   stability checks.
6. If Docker/PostgreSQL is needed by validation, confirm Docker is available
   before starting a long run:

   ```bash
   if ! docker info >/dev/null 2>&1; then
     command -v open >/dev/null 2>&1 && open -a Docker || true
     for i in $(seq 1 60); do
       docker info >/dev/null 2>&1 && break
       sleep 5
     done
   fi
   docker info >/dev/null
   docker compose up -d postgres
   ```

## Per-Spec Loop

For each queued spec in ascending order, starting with `queue.json.next_spec`:

1. Set the active feature only through the normal Spec Kit phase flow. Do not
   hand-edit `.specify/feature.json` except to recover an interrupted run where
   it points at the wrong already-created feature directory.
2. Run these phase skills in order using the generated phase prompt file for
   the active spec:
   - `speckit-specify`
   - `speckit-clarify`
   - `speckit-plan`
   - `speckit-tasks`
   - `speckit-analyze`
   - `speckit-implement`
3. For `speckit-specify`, use `specify.md` exactly, including
   `SPECIFY_FEATURE_DIRECTORY` and `GIT_BRANCH_NAME`.
4. For clarification, auto-answer only low-risk questions covered by the
   roadmap document, existing specs, repository patterns, or generated policy.
   Record every auto-choice in `spec.md` under `## Clarifications` with
   `(autopilot)`.
5. Stop and ask the user only when the answer changes tenant isolation, role
   boundaries, secret handling, destructive data behavior, production provider
   calls, real external side effects, irreversible migration behavior,
   approval/resume semantics, raw prompt/completion exposure, raw test
   transcript exposure, credential readiness behavior, or publish-gate trust
   semantics.
6. Run analysis after task generation. Treat CRITICAL findings as blockers.
   Auto-remediate CRITICAL/HIGH findings only when the fix is local to
   `spec.md`, `plan.md`, or `tasks.md` and directly implied by the roadmap or
   established repo patterns. Rerun analysis after remediation, up to two
   loops. Do not implement with remaining CRITICAL findings.
7. Implement only the active spec's tasks. Mark tasks complete as work lands.
8. If the spec adds, removes, renames, or behaviorally changes any public JSON,
   admin JSON, workflow, prompt/profile, test-bench, runtime, operations, or
   workflow setup API, update `curl_testing.md` in the same spec before
   validation. If no API changed, record that decision in `status.json`.
9. Update the active spec's `status.json` after every phase with phase name,
   artifact paths, blockers, remediation, validation evidence, and docs/curl
   decisions.
10. Update the active spec's matching phase in `queue.json` to `completed`
    after each phase completes. Validate queue edits with:

    ```bash
    jq . specs/_autopilot/<roadmap-dir>/queue.json
    ```

## Validation After Every Spec

Validation is mandatory before moving to the next spec.

1. Ensure implementation produced required QA artifacts:
   - `qaNNN.md`
   - `qaNNN_ui.md`
   - `.env.qaNNN`
   - `qaNNN_user_guide.md`
   - review notes requested by tasks
2. Reconcile the generated `validation.yml` with real routes, UI actions,
   seeded data, and browser journeys from the implementation. If a generated
   smoke route is stale or too shallow, update only that spec's
   `validation.yml`.
3. Run QA document validation:

   ```bash
   bash .specify/extensions/qa-docs/scripts/bash/validate-qa-documents.sh "$FEATURE_DIR"
   ```

4. Run API/database/backend/frontend quality validation:

   ```bash
   uv run python scripts/qa/run_spec_qa.py specs/_autopilot/<roadmap-dir>/NNN-slug/validation.yml
   ```

5. Run Playwright UI validation when the spec has browser behavior:

   ```bash
   uv run python scripts/qa/run_playwright_ui.py specs/_autopilot/<roadmap-dir>/NNN-slug/validation.yml --start-processes
   ```

6. Review `curl_testing.md` coverage for new or changed APIs. Run
   `multi-agent-curl-test` when API behavior changed or when the queue contract
   requires it:

   ```bash
   uv run python .agents/skills/multi-agent-curl-test/scripts/run_curl_test.py \
     --output-dir .data/curl_test_runs/qaNNN-after-spec
   ```

7. If validation fails, diagnose, fix the active spec only, and rerun the
   failed command plus downstream validation affected by the fix.
8. After all required validation passes, set the active spec `status` and
   `validation` to `completed`, ensure every phase is `completed`, and advance
   `queue.json.next_spec` to the next pending spec. When all specs complete,
   set `next_spec` to `null`.

## Final Roadmap Gate

After `queue.json.next_spec` is `null`, run the final stability gate from
`queue.json.final_stability_gate.commands` unless the user explicitly narrows
validation. Do not report the roadmap complete until the required final gate
passes or a blocker is documented.

Then update:

- `README.md`
- `user_guide.md`

Use the completed specs, QA guides, UI walkthroughs, and generated user guides
as source material. The docs update must describe newly available user-facing
behavior, browser navigation, setup or launch steps, configuration concepts,
and important guardrails. Keep API/curl details secondary unless the existing
docs already surface them.

Use the summary helper to gather implementation context before editing docs:

```bash
uv run python .agents/skills/autopilot-implement/scripts/summarize_autopilot_specs.py \
  specs/_autopilot/<roadmap-dir>
```

After editing docs, run focused docs checks or relevant test commands if the
repo has them. At minimum, inspect the changed sections for stale feature
names, fake/demo data language, raw secret examples, and route instructions
that bypass visible UI navigation.

## Stop Conditions

Stop the roadmap run and report clearly when any of these happen:

- Security, tenant isolation, audit, redaction, credential, secret, production
  resource, or external-side-effect behavior is ambiguous.
- A command would reset or mutate a database other than the active QA database
  or the dedicated `multi_agent_curl_test` database.
- A spec requires real Auth0, Telegram, provider, credential, connector, model,
  or outbound calls that are not explicitly mocked or approved in its
  artifacts.
- A production UI would synthesize fake workflows, fake agents, fake prompts,
  fake profiles, fake evidence, fake runs, or sample interaction records.
- A new or changed API cannot be represented safely in `curl_testing.md`.
- Raw prompts, completions, secrets, credentials, provider payloads, test
  transcripts, private channel payloads, memory contents, stack traces, local
  filesystem paths, or unauthorized tenant labels would be exposed in UI,
  exports, screenshots, QA artifacts, logs, docs, or audit summaries.
- Publish readiness would rely on browser-only checks instead of backend-owned
  validation and evidence.
- Analysis still has CRITICAL findings after two remediation loops.
- QA docs, backend quality gates, frontend quality gates, API/database checks,
  Playwright, or final docs checks fail after a focused repair attempt.
- Existing unrelated user changes block implementation.

## Resume Checklist

When resuming, read:

- `queue.json`
- root and per-spec `status.json`
- `.specify/feature.json`
- git status
- the active feature's `tasks.md`
- latest validation output and Playwright output
- latest curl-test artifact directory
- `curl_testing.md`
- the source roadmap document from `queue.json.roadmap_file`
- `README.md` and `user_guide.md` if all specs are complete
