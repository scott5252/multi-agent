# QA007: Model Routing And Skill Configuration

## Goal

Validate that Spec `007` lets authorized reviewers configure and review
tenant-scoped model routing, prompt references, skill bindings, allowed tool
policies, outbound domain policies, secret references, credential requirements,
configuration history, safe authorization failures, and delivery evidence.

This guide is written for non-developers. It gives copy/paste commands,
explains what each command proves, and records current implementation limits so
reviewers know the difference between a failed test and a feature surface that
is not fully wired yet.

## What This Guide Covers

Use this as a standalone reviewer checklist for Spec `007`. It validates:

- Local QA environment setup with deterministic Acme and Globex tenants.
- Authentication with local principals for administrator, maintainer, auditor,
  and cross-tenant reviewer roles.
- Tenant global default model creation and activation.
- Workflow, agent, and step model override creation.
- Prompt reference creation and prompt precedence behavior.
- Model preview showing deterministic source scopes.
- Configuration history showing actor, reason, scope, prior/new version ids,
  timestamp, and safe redacted summaries.
- Stale expected-version activation failure.
- Skill binding, allowed tool policy, outbound policy, secret-reference, and
  credential-requirement version creation.
- Fail-closed tool preview behavior and secret hygiene checks.
- Cross-tenant history denial.
- Run provenance endpoint shape.
- Admin web template availability for model routing, history, and run
  provenance views.
- Required reviewer evidence: Ruff, format, mypy, focused Spec 007 tests, and
  full coverage gate.

Important current-implementation note: this QA guide validates the Spec `007`
implementation currently present in this repository. The API can create
versioned configuration records, activate them, preview model/prompt
resolution, list history, fail closed on tool preview, and expose an empty run
provenance shape. Full runtime first-use pinning, side-effect interception,
generic rollback API, run migration, and admin web route handlers are planned
by the spec but are not fully wired in this implementation slice. Those checks
are documented below as "expected current gap" so a reviewer can record them
clearly instead of treating them as ambiguous failures.

## How To Use This Guide

You need two terminal windows:

- Terminal A runs the API server and should stay open for the manual QA pass.
- Terminal B runs the `curl`, `jq`, and quality commands from the repository
  root.

Run the sections in order. The commands save responses into
`/tmp/qa007-*.json` files and store ids in shell variables such as
`$TENANT_MODEL_VERSION_ID`. Keep using the same Terminal B session so those
variables remain available.

If a command prints `null`, an empty value, or an HTTP status different from
the expected status, stop and inspect the saved `/tmp/qa007-*.json` file before
continuing.

What the most important terms mean:

- A **tenant default model** is the Acme-wide fallback model for model-backed
  execution when no workflow, agent, or step override applies.
- A **model override** is a more specific model choice. Precedence is step,
  then agent, then workflow, then tenant default.
- A **prompt reference** is an immutable prompt version pointer. Prompt
  precedence is step, then agent, then workflow. There is no tenant-global
  prompt fallback.
- A **configuration version** is a saved immutable record with a version id,
  reason, actor, scope, and status.
- An **active pointer** is the current active version for one configuration
  kind and scope.
- A **safe summary** is audit text that must not expose raw prompts, raw
  secrets, credential values, provider tokens, or unauthorized run content.
- **Fail closed** means the platform denies access instead of guessing or
  leaking protected details.

## Environment

Run these setup steps from the repository root.

1. Copy the QA environment file into the app's `.env`:

   ```bash
   cp specs/007-model-skill-routing/.env.qa007 .env
   ```

   Expected: no output. This makes the app use local-principal auth and the
   PostgreSQL QA database `multi_agent_platform_qa007` on
   `127.0.0.1:5432`.

   Do not also export a separate `DATABASE_URL` unless you intend to run QA007
   against another PostgreSQL database and seed that database instead. The QA
   env file intentionally includes every setting needed for this local pass.
   If you export values manually, quote `LOCAL_PRINCIPAL_CATALOG_JSON`,
   `AUTH0_ALGORITHMS`, and `STATIC_SECRETS_JSON` because they are JSON.

2. Confirm `curl` and `jq` are installed:

   ```bash
   curl --version | head -1
   jq --version
   ```

   Expected: each command prints a version. If `jq` is unavailable, copy each
   returned id manually into the shell variables shown below.

3. Install dependencies:

   ```bash
   uv sync
   ```

   Expected: command completes without an error.

4. Start PostgreSQL:

   ```bash
   docker compose up -d postgres
   ```

   Expected: Docker starts the local `postgres:16-alpine` service. If it was
   already running, Docker reports that it is up to date.

5. Create the dedicated QA007 PostgreSQL database if it does not already
   exist:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -U postgres -d postgres -tc "SELECT 1 FROM pg_database WHERE datname = '\''multi_agent_platform_qa007'\''" | grep -q 1 || createdb -U postgres multi_agent_platform_qa007'
   ```

   Expected: no output. This keeps QA007 data separate from the default local
   `multi_agent_platform` database.

6. Apply database migrations:

   ```bash
   uv run alembic upgrade head
   ```

   Expected: command completes without an error and creates or updates
   PostgreSQL tables in `multi_agent_platform_qa007`.

7. Seed the Acme and Globex tenant rows:

   ```bash
   docker compose exec -T postgres psql -U postgres -d multi_agent_platform_qa007 <<'SQL'
   INSERT INTO tenants (
     tenant_id, slug, display_name, status, created_at, updated_at
   ) VALUES
     ('11111111-1111-1111-1111-111111111111', 'acme', 'Acme', 'active', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP),
     ('22222222-2222-2222-2222-222222222222', 'globex', 'Globex', 'active', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP)
   ON CONFLICT (tenant_id) DO NOTHING;
   SQL
   ```

   Expected: `INSERT 0 2` on the first run. On later runs, PostgreSQL may
   report `INSERT 0 0` because the tenant ids already exist.

   What this proves: the QA principals can authenticate against real tenant
   rows in PostgreSQL.

8. In Terminal A, start the API and leave it running:

   ```bash
   uv run uvicorn multi_agent_platform.api.main:app
   ```

   Expected: the server logs say Uvicorn is running on
   `http://127.0.0.1:8000`. Do not close this terminal until all manual QA
   sections are complete.

9. Optional worker parity check:

   ```bash
   uv run python -m multi_agent_platform.workers.main
   ```

   Expected: the worker starts without an error. The manual configuration API
   checks below do not require a worker.

## Model Routing: Tenant Default

This section proves that an administrator can create one active tenant-scoped
global default model. This is the fallback for Acme model-backed execution.

1. Create and activate the Acme tenant default model:

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa007-model-default.json -w "%{http_code}" \
     -X POST http://127.0.0.1:8000/admin/config/model-routing \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -d '{
       "scope": {"tenant_id": "'"$ACME_TENANT_ID"'"},
       "provider_key": "openai",
       "model_id": "gpt-5.4",
       "routing_parameters": {"temperature": 0.2},
       "activate": true,
       "reason": "QA007 set Acme tenant default model"
     }')
   cat /tmp/qa007-model-default.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   TENANT_MODEL_VERSION_ID=$(jq -r '.version_id' /tmp/qa007-model-default.json)
   echo "TENANT_MODEL_VERSION_ID=$TENANT_MODEL_VERSION_ID"
   ```

   Expected:

   - `HTTP_STATUS=201`
   - `config_kind` is `model_routing`
   - `active` is `true`
   - `scope.tenant_id` is the Acme tenant id
   - `redacted_summary.provider_key` is `openai`
   - `redacted_summary.model_id` is `gpt-5.4`
   - `TENANT_MODEL_VERSION_ID` prints a UUID, not `null`

   What this proves: the platform can create an immutable model routing
   version and activate it as the tenant default.

2. Try to create a tenant default without a reason:

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa007-model-default-missing-reason.json -w "%{http_code}" \
     -X POST http://127.0.0.1:8000/admin/config/model-routing \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -d '{
       "scope": {"tenant_id": "'"$ACME_TENANT_ID"'"},
       "provider_key": "openai",
       "model_id": "gpt-5.4-mini",
       "activate": true,
       "reason": ""
     }')
   cat /tmp/qa007-model-default-missing-reason.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   jq -r '.detail.category, .detail.message' /tmp/qa007-model-default-missing-reason.json
   ```

   Expected:

   - `HTTP_STATUS=422`
   - `detail.category` is `validation_failed`
   - Message says a non-empty reason is required

   What this proves: configuration changes require human-readable audit
   reasons.

## Troubleshooting

- `401 missing local principal header or cookie`: include
  `-H "X-Local-Principal: tenant-admin-acme"` or another QA007 principal.
- `401 unknown local principal`: confirm `.env` was copied from
  `specs/007-model-skill-routing/.env.qa007` and restart the API.
- `403 authorization_failed`: check that the principal belongs to the same
  tenant id in the request. Globex must not read Acme history or provenance.
- `422 validation_failed`: check that `reason` is non-empty and required JSON
  fields are present.
- `422 missing_prompt_version`: tenant-global prompt references are invalid;
  use workflow, agent, or step scope.
- `409 stale_configuration`: the expected active version id did not match the
  current active pointer. Refresh history or preview before retrying.
- `500` from a configuration request: inspect Terminal A logs and confirm
  Docker PostgreSQL is running, the `multi_agent_platform_qa007` database
  exists, and migrations ran against that database.
- `jq: command not found`: install `jq` or copy ids manually from the JSON
  response into the matching shell variable.
- `null` id variables: inspect the matching `/tmp/qa007-*.json` file; do not
  continue until the id prints as a UUID.
