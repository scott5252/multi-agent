# QA018: User And Tenant Membership Administration

## Goal

This guide proves that the Membership Administration feature lets authorized
platform admins and tenant admins manage invitations, principal identities,
tenant memberships, role grants, principal status, and access-history evidence
without storing passwords or leaking raw user identifiers in screenshots.

The reviewer should finish with evidence that `/admin/memberships` works in
local-principal mode, JSON APIs enforce the same tenant boundaries as the UI,
invitation replay is idempotent, tenant admins cannot assign platform roles,
role changes are visible on the next protected request, and audit/history rows
use safe summaries.

## What This Guide Covers

- Dedicated `qa018` environment setup with PostgreSQL database
  `multi_agent_platform_qa018`.
- Local login principals for platform admin, Acme tenant admin, Acme tenant
  user, Acme auditor, and Globex tenant admin.
- Manual API evidence for membership snapshots, invitations, Auth0 subject
  linking, role grants, revocation, status changes, tenant isolation, and
  redaction.
- Browser evidence for the server-rendered Membership Administration page.
- Required automated evidence, including focused tests, full coverage, Ruff,
  formatting, mypy, Spec Kit API validation, and Playwright UI validation.

## Environment

install dependencies:

```bash

```

Expected: `.env` exists, dependency sync finishes, and the two artifact
directories exist.

Start PostgreSQL and reset the dedicated QA database:

```bash
docker compose up -d postgres

uv run alembic upgrade head
```

Expected: PostgreSQL is running, the `multi_agent_platform_qa018` database is
fresh, and Alembic upgrades through `0018_membership_admin`.

What this proves: the membership tables are created from migrations, not from
test-only metadata.

```bash
  tenant_id,

  status,

  updated_at
```

## Platform Admin Snapshot And Invitation Replay

Create an Acme invitation as the platform admin:

```bash
HTTP_STATUS=$(
  curl --silent --output /tmp/qa018-invite-create.json --write-out '%{http_code}' \
    -X POST "$QA018_BASE_URL/admin/memberships/api/invitations" \
    -H "X-Local-Principal: platform-admin" \
    -H "Content-Type: application/json" \
    -d "{\"tenant_id\":\"$QA018_ACME_TENANT\",\"email\":\" $QA018_INVITE_EMAIL \",\"requested_roles\":[\"tenant_user\"],\"idempotency_key\":\"qa018-acme-reviewer\"}"
)
printf '%s\n' "$HTTP_STATUS" | tee /tmp/qa018-invite-create.status
jq . /tmp/qa018-invite-create.json
```

Expected: `HTTP_STATUS` is `201`, `masked_email` is present,
`email_hash` is present, `requested_roles` contains `tenant_user`, and the raw
email casing plus whitespace are not echoed back.

What this proves: invitations normalize operational email input but render
safe summaries for API evidence.

Submit the same invitation again:

```bash
HTTP_STATUS=$(
  curl --silent --output /tmp/qa018-invite-replay.json --write-out '%{http_code}' \
    -X POST "$QA018_BASE_URL/admin/memberships/api/invitations" \
    -H "X-Local-Principal: platform-admin" \
    -H "Content-Type: application/json" \
    -d "{\"tenant_id\":\"$QA018_ACME_TENANT\",\"email\":\"$QA018_INVITE_EMAIL\",\"requested_roles\":[\"tenant_user\"],\"idempotency_key\":\"qa018-acme-reviewer\"}"
)
printf '%s\n' "$HTTP_STATUS" | tee /tmp/qa018-invite-replay.status
jq '{user_invitation_id, replayed, masked_email, email_hash}' /tmp/qa018-invite-replay.json
```

Expected: `HTTP_STATUS` is `201`, `replayed` is `true`, and
`user_invitation_id` matches the first response.

What this proves: active invitation replay is idempotent for the same tenant,
normalized email, requested roles, and idempotency key.

Check the snapshot after invitation creation:

## Auth0 Subject Linking

Link a safe Auth0 subject as the platform admin:

```bash
HTTP_STATUS=$(
  curl --silent --output /tmp/qa018-link-auth0.json --write-out '%{http_code}' \
    -X POST "$QA018_BASE_URL/admin/memberships/api/principals/link" \
    -H "X-Local-Principal: platform-admin" \
    -H "Content-Type: application/json" \
    -d "{\"auth0_subject\":\"$QA018_AUTH0_SUBJECT\",\"email\":\"qa018.reviewer@example.test\",\"display_name\":\"QA018 Reviewer\"}"
)
printf '%s\n' "$HTTP_STATUS" | tee /tmp/qa018-link-auth0.status
```

`subject_display` is masked, `masked_email` is masked, and no password field

references, not passwords.

## Troubleshooting

- `401 missing local principal header or cookie`: pass
  `X-Local-Principal` for API calls or sign in through local login.
- `403 membership action denied`: confirm the selected principal and tenant id
  match the action. Acme tenant admins cannot act on Globex or platform roles.
- `404 membership not found`: use a fresh snapshot and copy the current
  `tenant_membership_id`.
- Empty principal table: call the protected snapshot route once as each local
  principal to bootstrap the local identity rows.
- Raw mixed-case email appears in `/tmp/qa018-*`: keep the file as evidence and
  treat it as a regression, except for the command body you typed locally.
- Docker cannot start PostgreSQL: ensure Docker Desktop or the local Docker
  service is running, then rerun the reset command.
- Playwright cannot find `platform-admin`: confirm `.env` came from
  `.env.qa018` before starting the server.
