# QA024: Automatic Test Bench Evidence Integration In Workflow Publish Gates

## Goal

Validate that workflow draft validation, publish gate evaluation, and final
publication use current repository-backed Agent Test Bench evidence for
required suites.

This QA pass proves that a workflow cannot be published just because a manual
document field says a suite passed.

It also proves that accepted evidence must belong to the same tenant, target
the same workflow draft, target the current draft revision, and have a passing
run status.

## What This Guide Covers

- Local setup for `multi_agent_platform_qa024`.
- Local-principal login for platform, Acme, Globex, and Acme reviewer personas.
- Workflow Registry pages under `/admin/workflows/ui`.
- Agent Test Bench pages under `/admin/agent-tests/ui`.
- Required test declarations in workflow draft documents.
- Repository-backed lookup of required suite runs.
- Missing evidence, failing evidence, stale evidence, and wrong-target evidence.
- Cross-tenant denial without leaking another tenant's suite details.
- Publish gate rendering of required, passing, missing, failing, and stale counts.
- Safe evidence pins in publish gate summaries and published version metadata.
- Redaction scans for fixture values, transcript snippets, target names from denied tenants, and secret-looking values.
- Focused tests and full quality gates.

Current implementation note: QA024 exercises repository-backed evidence for
workflow draft targets. Platform-scope drafts with tenant required suites fail
closed because there is not yet a platform-owned suite target policy for this
gate. Published evidence pins are safe summaries, not raw test output.

## How To Use This Guide

Use two terminal windows from the repository root.

- Terminal A runs the API server and stays open.
- Terminal B runs setup, browser support commands, API smoke checks, SQL checks, and quality gates.

Use the same Terminal B session for shell variables.

Save command output under `/tmp/qa024-*` so reviewer evidence is easy to collect.

Stop if any command exits non-zero when the step says it should succeed.

Important terms:

- A required suite is a workflow document requirement that references an Agent Test Suite.
- Current evidence means a latest persisted run for the same suite, tenant, target type, target id, and target version.
- Target version means the active workflow draft revision id at validation time.
- Stale evidence means a run exists but it targets an older revision or otherwise mismatched target.
- Missing evidence means no readable same-tenant suite or no usable run is available.
- Failed evidence means the latest current run exists and did not pass.
- Safe summary means reviewer-visible text that does not include raw fixtures, prompts, transcripts, secrets, or other tenant names from denied evidence.

## Manual Workflow Evidence Check

1. Open the local login page:

```text
http://127.0.0.1:8000/auth/local-login?redirect_to=/admin/workflows/ui
```

Expected: the Local Login page lists `tenant-admin-acme`.

What this proves: a reviewer can use the browser workflow without Auth0.

2. Sign in as `tenant-admin-acme` and create a tenant workflow draft.

Expected: the Workflow Registry shows the draft in Acme tenant scope.

What this proves: the draft belongs to the same tenant used by the required test suite.

3. Create or select an Agent Test Suite in `/admin/agent-tests/ui` for the same tenant.

Expected: the suite target is the workflow draft, and the target version is the current draft revision.

What this proves: the suite can produce current evidence for this exact draft revision.

4. Add a deterministic case and run the suite in `mock_model` mode.

Expected: the run status is `passed`, and diagnostics show safe summaries only.

What this proves: the repository now has acceptable current passing evidence.

5. Return to the workflow editor and add a required test declaration for that suite.

Expected: the workflow editor saves and records a new draft revision.

What this proves: the workflow document now declares the suite as required for publish readiness.

6. Validate the draft.

Expected: the validation result has zero blocking required-test findings.

What this proves: validation accepted the persisted same-tenant passing run.

7. Open the publish gate page.

Expected: the page shows Required Test Evidence, one required suite, one passing suite, zero missing, zero failing, and zero stale.

What this proves: the publish gate UI is using repository evidence rather than manual document status.

8. Publish the draft.

Expected: the published version summary includes safe required-test evidence pins.

What this proves: final publication rechecked and pinned current evidence.

## Negative Path Checks

Change the workflow draft after a passing run and validate again.

Expected: the required-test summary reports stale evidence for the old revision.

What this proves: the gate does not reuse an old run after a draft changes.

Run a required suite and force a failing result.

Expected: validation and publish gate evaluation report failed evidence.

What this proves: current but non-passing evidence still blocks publication.

Reference a suite id that does not exist in Acme.

Expected: validation reports missing evidence with a safe message.

What this proves: missing repository evidence fails closed.

Reference a Globex suite while signed in as Acme.

Expected: validation reports unavailable or missing evidence without showing Globex suite names.

What this proves: cross-tenant denial does not leak protected details.

Set a workflow document `latest_result_status` value to `passed` without running the suite.

Expected: validation still blocks.

What this proves: manual status fields cannot bypass repository-backed evidence.

## Troubleshooting

If login does not show QA principals, confirm `.env` was copied from `.env.qa024` and restart the API.

If validation cannot find a suite, confirm the suite and workflow draft share the Acme tenant id.

If evidence is stale, confirm the suite run target version equals the current workflow draft revision id.

If a publish gate is still blocked after a passing run, save the draft again only if needed, rerun the suite against the new revision, then validate again.

If a cross-tenant check reveals a Globex suite name to an Acme reviewer, stop and mark it as a security regression.

If Docker is unavailable, run the focused tests with `--no-cov` and record that manual PostgreSQL QA could not be completed on this machine.

If the QA script fails during setup, inspect `/tmp/qa024-api.log` and rerun the failing command manually.

If Playwright screenshots are missing, check that port `8000` is free and that `output/playwright/qa024_ui` exists.
