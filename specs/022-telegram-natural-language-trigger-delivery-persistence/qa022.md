# QA022: Telegram Natural-Language Trigger Delivery Persistence

## Goal

Validate that tenant Telegram aliases can be configured, linked to persistent
Telegram identities, triggered by natural-language messages, replayed
idempotently, and delivered through a mocked Bot API boundary without exposing
raw secrets or cross-tenant data.

## What This Guide Covers

- Tenant Telegram enablement for Acme.
- Command alias creation for `Morning briefing`.
- Persistent link-token consumption.
- Persistent Telegram identity lookup.
- Natural-language webhook routing.
- Duplicate update replay through `telegram_update_receipts`.
- Mocked `sendMessage` delivery evidence.
- Disabled-tenant denial.
- Redaction checks for tokens, chat ids, user ids, prompts, and results.
- Focused automated tests and full quality gates.

## How To Use This Guide

Run the commands from the repository root. Keep one terminal for the API, one
for optional worker execution, and one for curl and database checks. Save every
response under `/tmp/qa022-*` so a reviewer can compare evidence without
rerunning the whole scenario.

## Configure Tenant Telegram

Read the current Acme Telegram configuration:

```bash
curl --fail --silent \
  -H "$ACME_HEADER" \
  "$BASE_URL/admin/telegram/api/config?tenant_id=$ACME_TENANT" \
  | tee /tmp/qa022-config-before.json
```

Expected: the response includes `enabled`, `revision_token`, and
`command_ready`.

Enable the tenant configuration:

```bash
REVISION=$(python - <<'PY'
import json
print(json.load(open('/tmp/qa022-config-before.json'))['revision_token'])
PY
)
curl --fail --silent \
  -H "$ACME_HEADER" \
  -H 'Content-Type: application/json' \
  -X POST "$BASE_URL/admin/telegram/api/config" \
  -d "{\"tenant_id\":\"$ACME_TENANT\",\"enabled\":true,\"protected_commands\":[\"/run\",\"/status\"],\"status_note\":\"QA022 ready\",\"revision_token\":\"$REVISION\"}" \
  | tee /tmp/qa022-config-enabled.json
```

Expected: `enabled` is true and the response does not contain
`local-dev-secret`.

What this proves: runtime alias routing can only proceed after tenant
configuration is explicitly enabled.

## Create The Morning Briefing Alias

Create the alias:

```bash
curl --fail --silent \
  -H "$ACME_HEADER" \
  -H 'Content-Type: application/json' \
  -X POST "$BASE_URL/admin/telegram/api/aliases" \
  -d "{\"tenant_id\":\"$ACME_TENANT\",\"alias_text\":\"Morning briefing\",\"published_workflow_version_id\":\"$WORKFLOW_VERSION\",\"description\":\"Daily Intelligence Briefing\",\"protected\":true,\"enabled\":true}" \
  | tee /tmp/qa022-alias-created.json
```

Expected: the response has `alias_normalized` set to `morning briefing`.

List aliases:

```bash
curl --fail --silent \
  -H "$ACME_HEADER" \
  "$BASE_URL/admin/telegram/api/aliases?tenant_id=$ACME_TENANT" \
  | tee /tmp/qa022-alias-list.json
```

Expected: the list contains exactly the QA alias and the configured workflow
version.

Try cross-tenant access:

```bash
HTTP_STATUS=$(curl --silent --output /tmp/qa022-globex-denied.json --write-out '%{http_code}' \
  -H "$GLOBEX_HEADER" \
  "$BASE_URL/admin/telegram/api/aliases?tenant_id=$ACME_TENANT")
printf '%s\n' "$HTTP_STATUS" | tee /tmp/qa022-globex-denied.status
```

Expected: `HTTP_STATUS` is `403`.

What this proves: alias configuration is tenant isolated.

## Link Telegram Identity

Issue a token:

```bash
curl --fail --silent \
  -H "$ACME_HEADER" \
  -X POST "$BASE_URL/admin/telegram/api/link-tokens?tenant_id=$ACME_TENANT" \
  | tee /tmp/qa022-link-token.json
```

Expected: the response includes `link_token` once and a token fingerprint that
is not the raw token.

Send the link command:

```bash
LINK_TOKEN=$(python - <<'PY'
import json
print(json.load(open('/tmp/qa022-link-token.json'))['link_token'])
PY
)
curl --fail --silent \
  -H 'Content-Type: application/json' \
  -X POST "$BASE_URL/channels/telegram/webhook/local-dev-secret" \
  -d "{\"update_id\":22001,\"message\":{\"chat\":{\"id\":123456789},\"from\":{\"id\":987654321},\"text\":\"/link $LINK_TOKEN\"}}" \
  | tee /tmp/qa022-link-response.json
```

Expected: the response says Telegram linked to `tenant-admin-acme`.

List identities:

```bash
curl --fail --silent \
  -H "$ACME_HEADER" \
  "$BASE_URL/admin/telegram/api/identities?tenant_id=$ACME_TENANT" \
  | tee /tmp/qa022-identities.json
```

Expected: the response includes `123***789` and `987***321`, and does not
include the full user or chat identifier.

What this proves: link state survived through PostgreSQL-backed token
consumption and masked identity summaries.

## Trigger Morning Briefing

Send the natural-language alias:

```bash
curl --fail --silent \
  -H 'Content-Type: application/json' \
  -X POST "$BASE_URL/channels/telegram/webhook/local-dev-secret" \
  -d '{"update_id":22002,"message":{"chat":{"id":123456789},"from":{"id":987654321},"text":"Morning briefing"}}' \
  | tee /tmp/qa022-trigger-response.json
```

Expected: the response includes `alias`, `run_id`, and `delivered: true`.

Repeat the same update id:

```bash
curl --fail --silent \
  -H 'Content-Type: application/json' \
  -X POST "$BASE_URL/channels/telegram/webhook/local-dev-secret" \
  -d '{"update_id":22002,"message":{"chat":{"id":123456789},"from":{"id":987654321},"text":"Morning briefing"}}' \
  | tee /tmp/qa022-trigger-duplicate.json
diff /tmp/qa022-trigger-response.json /tmp/qa022-trigger-duplicate.json
```

Expected: the duplicate response is byte-for-byte identical.

What this proves: Telegram retry handling replays the persisted receipt instead
of creating another run or delivery.

## Database Evidence

Inspect persisted aliases and receipts:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform_qa022 <<'SQL' | tee /tmp/qa022-db-alias-receipts.txt
SELECT alias_text, alias_normalized, enabled, protected
FROM telegram_command_aliases
ORDER BY alias_normalized;
SELECT telegram_update_id, action_type, run_id IS NOT NULL AS has_run
FROM telegram_update_receipts
ORDER BY telegram_update_id;
SQL
```

Expected: `Morning briefing` is enabled and update `22002` has a run.

Inspect delivery attempts:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform_qa022 <<'SQL' | tee /tmp/qa022-db-delivery.txt
SELECT channel_type, event_type, delivery_status, provider_message_id, destination_fingerprint IS NOT NULL AS safe_destination
FROM notification_delivery_attempts
ORDER BY created_at;
SQL
```

Expected: at least one `telegram` terminal delivery is `delivered` with a safe
destination fingerprint.

What this proves: final Telegram delivery has durable operational evidence.

## Troubleshooting

- If `/admin/telegram/api/config` returns 401, check `AUTH_MODE` and the local
  principal header.
- If alias creation returns 403, confirm the principal has
  `telegram-config:write`.
- If `/link` returns unauthorized, issue a fresh token and check the token was
  copied from the one-time response.
- If `Morning briefing` returns missing input, confirm the alias row is enabled
  and normalized as `morning briefing`.
- If alias trigger returns unavailable delivery, confirm tenant Telegram config
  is enabled and `TELEGRAM_PROVIDER_TOKEN_REF` is configured.
- If duplicate replay differs, inspect `telegram_update_receipts` for update
  `22002`.
- If delivery evidence is missing, inspect `notification_delivery_attempts` and
  the API logs for the trace id from `/tmp/qa022-trigger-response.json`.
- If redaction checks fail, stop review and attach the leaked file path.
- If Playwright cannot log in, open
  `http://127.0.0.1:8000/auth/local-login?redirect_to=/admin/telegram`.
- If migrations fail, reset only `multi_agent_platform_qa022` and rerun
  `uv run alembic upgrade head`.
