# QA006: User Interaction Channels

## Goal

Validate that Web UI, Telegram, and Web API channels all use the same workflow
run interaction model for invocation, status, progress, approvals, results,
notification subscription registration, callback registration, and artifact
download URL grants.

## What This Guide Covers

Use this guide as a standalone reviewer checklist for Spec `006`. It validates:

- Web API invocation, status, timeline, SSE, result, notification subscription
  registration, callback registration, approval, cancellation, artifact list,
  and artifact URL grant responses.
- Web UI run start, run detail rendering, support trace visibility, and SSE
  event endpoint behavior.
- Telegram link-token issuance, `/link`, protected commands, unlinked denial,
  provider secret handling, and duplicate `update_id` replay.
- Shared lifecycle names: `queued`, `running`, `waiting-for-input`,
  `completed`, `failed`, and `canceled`.
- Idempotency conflict handling and safe cross-tenant denial.
- QA evidence commands for Ruff, mypy, focused channel tests, and full coverage.

Important current-implementation note: the Spec `006` channel facade stores run
interaction state in the running FastAPI process. Keep the API process running
while you move between Web API, Web UI, and Telegram checks. The migration adds
the durable channel evidence tables, but this QA guide validates the current
in-process facade behavior. External notification delivery, external callback
delivery, and artifact byte serving are not performed by this implementation;
the API validates subscriptions, callback registrations, and short-lived
artifact URL grants.

## How To Use This Guide

This guide is written as a copy/paste QA script. You do not need to understand
the codebase to run it, but you do need two terminal windows:

- Terminal A runs the API server and should stay open for the full QA pass.
- Terminal B runs the `curl`, `jq`, and test commands below from the repository
  root.

Run the sections in order. The commands save responses into `/tmp/qa006-*.json`
files and store important ids in shell variables such as `$RUN_ID`. Keep using
the same Terminal B session so those variables remain available. If a command
prints `null`, an empty value, or an HTTP status different from the expected
status, stop and inspect the saved `/tmp/qa006-*.json` file before continuing.

What the most important terms mean:

- A **run** is one workflow execution request. It has one stable `run_id`.
- An **idempotency key** is a duplicate-protection key. The same key with the
  same request should return the same accepted outcome. The same key with
  different request content should be rejected with `idempotency_conflict`.
- A **tenant principal** is the test identity in `X-Local-Principal`. Acme and
  Globex are different tenants, so Globex must not see Acme runs.
- A **waiting prompt** is a human approval step. The start response gives a
  `run_id`; the status response gives the `waiting_prompt.prompt_id`.

## Web API Smoke Test

This section proves that the Web API can start a run and that the returned
`run_id` can be used to read status, timeline events, and result availability.

1. Start a run as the Acme tenant admin:

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa006-run-start.json -w "%{http_code}" \
     -X POST http://127.0.0.1:8000/runs \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -H "X-Idempotency-Key: qa006-run-001" \
     -d '{
       "workflow_id": "published-demo-workflow",
       "inputs": {"topic": "qa006"},
       "channel": "web_api"
     }')
   cat /tmp/qa006-run-start.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   RUN_ID=$(jq -r '.run_id' /tmp/qa006-run-start.json)
   echo "RUN_ID=$RUN_ID"
   ```

   Expected:

   - `HTTP_STATUS=202`
   - The JSON includes `run_id`, `state: "queued"`, `status_url`,
     `timeline_url`, `events_url`, and `trace_id`.
   - `RUN_ID=` prints a UUID. If it prints `null`, stop here because later
     commands depend on this value.

2. Fetch the run status using the returned `RUN_ID`:

   ```bash
   curl -s -H "X-Local-Principal: tenant-admin-acme" \
     "http://127.0.0.1:8000/runs/$RUN_ID/status" | tee /tmp/qa006-run-status.json

   jq -r '.run_id, .state, .progress_summary, .result_availability' \
     /tmp/qa006-run-status.json
   ```

   Expected:

   - `run_id` matches `$RUN_ID`.
   - `state` is one of `queued`, `running`, `waiting-for-input`, `completed`,
     `failed`, or `canceled`. For this local facade it should be `queued`.
   - `progress_summary` explains that the run was accepted through the channel
     facade.
   - `result_availability` is `unavailable` for this queued run.

3. Fetch the timeline:

   ```bash
   curl -s -H "X-Local-Principal: tenant-admin-acme" \
     "http://127.0.0.1:8000/runs/$RUN_ID/timeline?limit=100" | tee /tmp/qa006-run-timeline.json

   jq -r '.items[0].event_type, .items[0].state, .items[0].summary' \
     /tmp/qa006-run-timeline.json
   ```

   Expected: the first event type is `run_queued`, the state is `queued`, and
   the summary says the run was accepted through the channel facade.

4. Fetch result availability:

   ```bash
   curl -s -H "X-Local-Principal: tenant-admin-acme" \
     "http://127.0.0.1:8000/runs/$RUN_ID/result" | tee /tmp/qa006-run-result.json

   jq -r '.run_id, .state, .availability' /tmp/qa006-run-result.json
   ```

   Expected: `run_id` matches `$RUN_ID`, `state` is `queued`, and

## SSE Progress Stream

This section proves that a browser or API client can open a Server-Sent Events
stream for live progress. In the current local facade, the stream sends the
available timeline events, sends one heartbeat, and then completes.

1. Open the event stream for the run created in the Web API smoke test:

   ```bash
   curl -i -N -H "X-Local-Principal: tenant-admin-acme" \
     "http://127.0.0.1:8000/runs/$RUN_ID/events" | tee /tmp/qa006-events.txt
   ```

   Expected:

   - Response headers include `content-type: text/event-stream`.
   - The body includes an event with `event: run_queued`.
   - The body includes `event: heartbeat`.
   - The command returns to the shell after the heartbeat.

2. Reconnect with `Last-Event-ID: 1`. This simulates a client that already
   received event sequence `1` and only wants later events:

   ```bash
   curl -i -N -H "X-Local-Principal: tenant-admin-acme" \
     -H "Last-Event-ID: 1" \
     "http://127.0.0.1:8000/runs/$RUN_ID/events" | tee /tmp/qa006-events-resume.txt
   ```

   Expected: already-sent event sequence `1` is skipped. If no later events
   exist, the response may contain only `event: heartbeat`.

   What this proves: clients can resume from the last seen timeline event
   cursor instead of replaying events they already processed.

## Idempotency And Auth

This section proves two safety rules:

- Duplicate submissions from the same caller do not create duplicate runs.
- A user from another tenant cannot see protected run details.

1. Replay the exact same run-start request from the Web API smoke test. This is
   what "repeat the original `POST /runs`" means: same URL, same principal,
   same `X-Idempotency-Key`, and the exact same JSON body.

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa006-run-replay.json -w "%{http_code}" \
     -X POST http://127.0.0.1:8000/runs \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -H "X-Idempotency-Key: qa006-run-001" \
     -d '{
       "workflow_id": "published-demo-workflow",
       "inputs": {"topic": "qa006"},
       "channel": "web_api"
     }')
   cat /tmp/qa006-run-replay.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   REPLAY_RUN_ID=$(jq -r '.run_id' /tmp/qa006-run-replay.json)
   echo "ORIGINAL_RUN_ID=$RUN_ID"
   echo "REPLAY_RUN_ID=$REPLAY_RUN_ID"
   if [ "$REPLAY_RUN_ID" = "$RUN_ID" ]; then
     echo "PASS: replay returned the same run id"
   else
     echo "FAIL: replay created or returned a different run id"
   fi
   ```

   Expected:

   - `HTTP_STATUS=202`
   - `REPLAY_RUN_ID` exactly matches `ORIGINAL_RUN_ID`
   - The final line prints `PASS: replay returned the same run id`

   What this proves: the platform recognized a duplicate safe retry and reused
   the stored accepted outcome instead of creating another run.

2. Reuse the same idempotency key with different input. This should be rejected
   because the key was already used for the original payload.

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa006-run-idempotency-conflict.json -w "%{http_code}" \
     -X POST http://127.0.0.1:8000/runs \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -H "X-Idempotency-Key: qa006-run-001" \
     -d '{
       "workflow_id": "published-demo-workflow",
       "inputs": {"topic": "qa006-different-input"},
       "channel": "web_api"
     }')
   cat /tmp/qa006-run-idempotency-conflict.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   jq -r '.error.category, .error.message' /tmp/qa006-run-idempotency-conflict.json
   ```

   Expected:

   - `HTTP_STATUS=409`
   - `error.category` is `idempotency_conflict`

   What this proves: a caller cannot accidentally reuse an idempotency key for a
   different request and silently get the wrong outcome.

3. Try to read the Acme run as the Globex tenant admin:

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa006-cross-tenant-status.json -w "%{http_code}" \
     -H "X-Local-Principal: tenant-admin-globex" \
     "http://127.0.0.1:8000/runs/$RUN_ID/status")
   cat /tmp/qa006-cross-tenant-status.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   jq -r '.error.category, .error.message' /tmp/qa006-cross-tenant-status.json
   ```

   Expected:

   - `HTTP_STATUS=404`
   - `error.category` is `invalid_run_id`
   - The response does not reveal Acme run details such as timeline events,
     result data, artifacts, or requester identity.

   What this proves: tenant isolation is fail-closed. Cross-tenant run ids are
   treated as not found.

## Waiting Prompt

This section proves that a run in `waiting-for-input` exposes a prompt, accepts
one valid decision, and rejects stale decisions after the prompt has already
been answered.

1. Create a local waiting run. The special `_channel_state` value is a QA-only
   simulation input that makes the channel facade expose a waiting prompt:

   ```bash
   curl -s -X POST http://127.0.0.1:8000/runs \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -H "X-Idempotency-Key: qa006-waiting-001" \
     -d '{
       "workflow_id": "waiting-demo",
       "inputs": {"topic": "approval", "_channel_state": "waiting"},
       "channel": "web_api"
     }' | tee /tmp/qa006-waiting-start.json

   WAITING_RUN_ID=$(jq -r '.run_id' /tmp/qa006-waiting-start.json)
   echo "WAITING_RUN_ID=$WAITING_RUN_ID"
   ```

   Expected: the response includes a `run_id`. The start response does not
   include `waiting_prompt` or `prompt_id`; that is expected.

2. Fetch status to get the prompt details. The prompt id appears under
   `waiting_prompt.prompt_id` in this response:

   ```bash
   curl -s -H "X-Local-Principal: tenant-admin-acme" \
     "http://127.0.0.1:8000/runs/$WAITING_RUN_ID/status" | tee /tmp/qa006-waiting-status.json

   jq -r '.state, .waiting_prompt.prompt_id, (.waiting_prompt.allowed_actions | join(","))' \
     /tmp/qa006-waiting-status.json
   PROMPT_ID=$(jq -r '.waiting_prompt.prompt_id' /tmp/qa006-waiting-status.json)
   echo "PROMPT_ID=$PROMPT_ID"
   ```

   Expected:

   - `state` is `waiting-for-input`
   - `PROMPT_ID` prints a UUID
   - allowed actions are `approve,reject,resume,cancel`

   The status response should include this shape:

   ```json
   {
     "state": "waiting-for-input",
     "waiting_prompt": {
       "prompt_id": "PROMPT_ID",
       "prompt_version": 1,
       "allowed_actions": ["approve", "reject", "resume", "cancel"]
     }
   }
   ```

3. Approve the waiting prompt:

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa006-waiting-decision.json -w "%{http_code}" \
     -X POST "http://127.0.0.1:8000/runs/$WAITING_RUN_ID/approvals/$PROMPT_ID/decision" \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -H "X-Idempotency-Key: qa006-decision-001" \
     -d '{"action": "approve", "prompt_version": 1, "decision_payload": {}}')
   cat /tmp/qa006-waiting-decision.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   jq -r '.accepted, .run_status.state, .run_status.progress_summary' \
     /tmp/qa006-waiting-decision.json
   ```

   Expected:

   - `HTTP_STATUS=202`
   - `accepted` is `true`
   - `run_status.state` is `running`
   - `waiting_prompt` is gone from the latest run status

4. Submit the same prompt decision again with a new idempotency key. This is a
   stale prompt response because the prompt was already answered in step 3:

   ```bash
   HTTP_STATUS=$(curl -s -o /tmp/qa006-waiting-stale-decision.json -w "%{http_code}" \
     -X POST "http://127.0.0.1:8000/runs/$WAITING_RUN_ID/approvals/$PROMPT_ID/decision" \
     -H "Content-Type: application/json" \
     -H "X-Local-Principal: tenant-admin-acme" \
     -H "X-Idempotency-Key: qa006-decision-002" \
     -d '{"action": "approve", "prompt_version": 1, "decision_payload": {}}')
   cat /tmp/qa006-waiting-stale-decision.json
   echo "HTTP_STATUS=$HTTP_STATUS"
   jq -r '.accepted, .rejection_category, .run_status.state' \
     /tmp/qa006-waiting-stale-decision.json
   ```

   Expected:

   - `HTTP_STATUS=409`
   - `accepted` is `false`
   - `rejection_category` is `invalid_lifecycle_action`
   - the returned `run_status.state` remains `running`

   What this proves: only the first valid prompt decision changes the run.
   Later stale decisions return the latest status without mutating the run.

Cancellation check for an active, non-terminal run. Use the original queued
`RUN_ID` from the Web API smoke test, or use `WAITING_RUN_ID` after the approval
above has moved it to `running`. Do not use the completed artifact run for this
check because terminal runs return an invalid lifecycle error.

```bash
HTTP_STATUS=$(curl -s -o /tmp/qa006-cancel.json -w "%{http_code}" \
  -X POST "http://127.0.0.1:8000/runs/$RUN_ID/cancel" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: tenant-admin-acme" \
  -H "X-Idempotency-Key: qa006-cancel-001" \
  -d '{"reason": "qa requested cancellation"}')
cat /tmp/qa006-cancel.json
echo "HTTP_STATUS=$HTTP_STATUS"
jq -r '.state, .terminal_outcome, .progress_summary' /tmp/qa006-cancel.json
```

Expected: `HTTP_STATUS=202`, `state` is `canceled`, and `terminal_outcome` is
`canceled`. Repeating the same cancel command with the same idempotency key and
body should return the same accepted outcome.

## Troubleshooting

- `401`: include `X-Local-Principal: tenant-admin-acme` or sign in through the
  local login page.
- `404 invalid_run_id`: verify the run id belongs to the same tenant as the
  current principal.
- `409 idempotency_conflict`: use a new idempotency key or repeat the exact
  original payload. An idempotency key cannot be reused for different request
  content.
- `409 accepted: false` for a prompt decision: the prompt is stale or already
  answered; fetch latest status.
- Telegram protected command returns `unauthorized`: create a fresh link token
  and send `/link <token>` from the same chat/user pair.
- Telegram duplicate commands keep returning old data: use new `update_id`
  values, or restart the API to clear in-process replay state.
- A previously captured run id starts returning `404`: confirm the API server
  did not restart. Current QA run state is in-process.
- Artifact list is empty: use the completed local run payload with
  `"_channel_state": "completed"` to generate reviewable artifact metadata.
