# QA Guide For Spec 006

This guide explains how to test the full Spec `006` user interaction channel
flow. It is standalone: use the QA environment file in this directory and the
seed data below instead of copying setup from earlier specs.

Every step explains what you are doing, why it matters, and what success looks
like. The guide is meant for implementation reviewers, QA testers, and
operators validating Web UI, Telegram, and Web API behavior after the feature
is implemented.

## 1. What You Are Testing

Spec `006` delivers:

- one shared channel facade for Web UI, Telegram, and user-facing Web API
  workflow starts
- canonical run identifiers and lifecycle states: `queued`, `running`,
  `waiting-for-input`, `completed`, `failed`, and `canceled`
- status endpoints, timeline endpoints, result retrieval, SSE streaming
  updates, and polling fallback behavior
- terminal-state notifications for initiating users and explicit subscribers
- Telegram webhook linking, protected command handling, and duplicate update
  suppression
- approval, rejection, resume, and cancellation flows for waiting runs
- short-lived platform-authenticated artifact download URLs
- API callback registration, signed callback delivery attempts, and retry
  evidence
- channel-level auth, idempotency, rate-limit, audit, redaction, docs, README,
  PR review notes, and coverage evidence

## 2. Before You Start

You need:

- Python `3.12`
- `uv`
- Docker with Docker Compose
- a terminal for the API
- a second terminal for the runtime and delivery workers
- a browser for Web UI checks
- `curl` for Web API and Telegram webhook simulation

## 7. Web API Invocation And Status Flow

### 7.1 Start A Run

Run:

```bash
curl \
  -H "X-Local-Principal: channel-user-acme" \
  -H "Content-Type: application/json" \
  -H "X-Idempotency-Key: qa006-api-run-001" \
  -H "X-Request-ID: qa006-api-start-001" \
  -X POST \
  http://127.0.0.1:8000/runs \
  -d '{
    "workflow_id": "'"$QA006_PUBLISHED_WORKFLOW_VERSION_ID"'",
    "inputs": {
      "topic": "qa006 api status flow",
      "mode": "happy_path",
      "produce_artifact": true
    },
    "channel": "web_api"
  }'
```

Success looks like:

- the response status is `202`
- the response includes `run_id`
- the initial visible state is `queued` or `running`
- the response includes a trace id

Save the run id:


Success looks like:

- events are sent as `text/event-stream`
- lifecycle or timeline updates arrive while the run is active
- heartbeat events keep the connection alive
- after terminal state, the stream stops cleanly or sends a terminal snapshot

Resume from a known event:

```bash
curl -N \
  -H "X-Local-Principal: channel-user-acme" \
  -H "Last-Event-ID: <last_event_id>" \
  http://127.0.0.1:8000/runs/$QA006_RUN_ID/events
```

Success looks like:

- duplicate events before `Last-Event-ID` are not replayed as new updates
- missed later events are delivered when available

```bash

  -d '{
    "workflow_id": "'"$QA006_PUBLISHED_WORKFLOW_VERSION_ID"'",
    "inputs": {
      "topic": "qa006 approval flow",
      "mode": "requires_review",
      "requires_approval": true
    },
    "channel": "web_api"
  }'
```

Save the waiting run id:

```bash
export QA006_WAITING_RUN_ID=<run_id>
```

```bash

  -H "X-Local-Principal: channel-reviewer-acme" \
```

Success looks like:


```bash

  -H "X-Local-Principal: channel-reviewer-acme" \
  -H "Content-Type: application/json" \
  -H "X-Idempotency-Key: qa006-approve-001" \
```

Success looks like:

- the response status is `202`
- the run leaves `waiting-for-input`
- repeating the same request returns the stored accepted outcome
- changing the action with the same idempotency key returns
  `idempotency_conflict`

```bash

  -H "X-Local-Principal: channel-reviewer-acme" \
  -H "Content-Type: application/json" \
  -H "X-Idempotency-Key: qa006-stale-approve-001" \

    "prompt_version": '"$QA006_PROMPT_VERSION"',
```

- the response returns `invalid_lifecycle_action`
- the latest run status is included
- the run is not mutated
