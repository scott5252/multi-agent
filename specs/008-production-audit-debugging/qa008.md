# QA008: Production Audit And Debugging

## Goal

Validate that Spec `008` lets authorized administrators and auditors inspect
production-safe workflow run evidence without direct database access. The
checks cover chronological timelines, failed-run debugging, replay, lineage,
version-bundle visibility, runtime decision traces, notification delivery
state, secret-access audit metadata, capture gaps, redaction, exports,
authorization failures, documentation, and automated quality evidence.

This guide is written for non-developers. It gives copy/paste commands,
explains what each command proves, and calls out current implementation limits
so reviewers can distinguish a real failure from a feature slice that is
present but not fully connected to live workflow execution yet.

## What This Guide Covers

Use this as a standalone reviewer checklist for Spec `008`. It validates:

- Local QA environment setup with deterministic Acme and Globex tenants.
- Authentication with local principals for administrator, auditor, operator,
  and cross-tenant administrator roles.
- Clean PostgreSQL setup from scratch in `multi_agent_platform_qa008`.
- Deterministic audit-debugging seed data for completed, failed, and child
  runs.
- Timeline inspection with accepted, queued, started, waiting, resumed,
  completed, failed, correction/redaction, and child-run lifecycle events.
- Runtime trace visibility for agent handoff, contract validation, memory
  write, tool usage, model selection, notification delivery, and secret
  access.
- Safe failed-run debugging fields: failed stage, safe reason, failure
  category, and recommended investigation category.
- Replay endpoint shape and bounded replay sequence filtering.
- Parent-child lineage graph.
- Version bundle endpoint and safe configuration references.
- Notification delivery evidence and the current top-level notification
  projection gap.
- Secret-access metadata without raw secret values.
- Capture-gap markers for unavailable diagnostic trace data.
- Debug-evidence export route coverage and the current PostgreSQL export
  creation gap.
- Same-tenant authorization denial and cross-tenant denial audit records.
- Admin web template availability.
- Required reviewer evidence: Ruff, format, mypy, focused Spec 008 tests, and
  full coverage gate.

Important current-implementation note: this QA guide validates the Spec `008`
implementation currently present in this repository. The implemented API
exposes `/admin/runs/debug-search`, `/admin/runs/{workflow_run_id}/timeline`,
`/admin/runs/{workflow_run_id}/replay`, `/admin/runs/{workflow_run_id}/lineage`,
`/admin/runs/{workflow_run_id}/bundle`, and
`/admin/runs/{workflow_run_id}/exports`. Runtime audit capture builders,
redaction, repository persistence, timeline assembly, replay assembly,
authorization auditing, and docs are covered by automated tests. The manual
guide seeds deterministic audit records directly because there is not yet a
single end-to-end demo workflow endpoint that creates every Spec `008` trace
type. Search currently filters by `workflow_run_id`, `status`,
`failure_category`, and `limit`; the API accepts additional query parameters
from the spec, but those filters are not all applied by the repository yet.
Notification delivery is visible as a linked `notification_delivery` trace in
the timeline; the top-level `notifications` array is currently present but
empty in this implementation slice. Secret-access metadata is visible through
the `secret_access` trace and the audit table; raw secret values are never
seeded or returned. The export endpoint is registered and documented, but
manual PostgreSQL QA currently returns a `500` before export creation because
the idempotency lookup compares a PostgreSQL `json` column with `=`. Record
that as an expected current gap until the repository uses JSONB or a digest
for idempotency.

## How To Use This Guide

You need two terminal windows:

- Terminal A runs the API server and should stay open for the manual QA pass.
- Terminal B runs the setup, `curl`, `jq`, SQL verification, and quality
  commands from the repository root.

Run the sections in order. The commands save responses into
`/tmp/qa008-*.json` or `/tmp/qa008-*.html` files and store ids in shell
variables such as `$FAILED_RUN_ID`. Keep using the same Terminal B session so
those variables remain available.

If a command prints `null`, an empty value, or an HTTP status different from
the expected status, stop and inspect the saved `/tmp/qa008-*` file before
continuing.

What the most important terms mean:

- A **run timeline** is the chronological audit history for one workflow run.
- A **timeline event** is one state or decision point, such as accepted,
  started, failed, redaction, or secret access.
- A **runtime trace** explains a decision attached to a timeline event, such
  as tool use, model selection, handoff, memory write, notification delivery,
  or secret access.
- A **safe summary** is reviewer-visible text or JSON that must not expose raw
  secrets, credential values, prompt bodies, raw memory content, or large
  external payloads.
- A **capture gap** is an explicit marker showing that non-security diagnostic
  evidence was unavailable instead of silently missing.
- **Fail closed** means the platform denies access instead of guessing,
  continuing, or leaking protected details.
- A **debug-evidence export** is a redacted export request record for support
  or audit review. This implementation creates export metadata; artifact
  upload/finalization is not part of the manual API flow.

## Environment

Run these setup steps from the repository root.

1. Copy the QA environment file into the app's `.env`:

   ```bash
   cp specs/008-production-audit-debugging/.env.qa008 .env
   ```

   Expected: no output. This makes the app use local-principal auth and the
   PostgreSQL QA database `multi_agent_platform_qa008` on `127.0.0.1:5432`.

   Do not also export a separate `DATABASE_URL` unless you intend to run QA008
   against another PostgreSQL database and seed that database instead. The QA
   env file intentionally includes every setting needed for this local pass.

2. Confirm `curl` and `jq` are installed:

   ```bash
   curl --version | head -1
   jq --version
   ```

   Expected: each command prints a version. If `jq` is unavailable, copy each
   returned id manually into the shell variables shown below.

3. Install dependencies:

   ```bash
   uv sync
   ```

   Expected: command completes without an error.

4. Start PostgreSQL:

   ```bash
   docker compose up -d postgres
   ```

   Expected: Docker starts the local `postgres:16-alpine` service. If it was
   already running, Docker reports that it is up to date.

5. Create the dedicated QA008 PostgreSQL database if it does not already
   exist:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -U postgres -d postgres -tc "SELECT 1 FROM pg_database WHERE datname = '\''multi_agent_platform_qa008'\''" | grep -q 1 || createdb -U postgres multi_agent_platform_qa008'
   ```

   Expected: no output. This keeps QA008 data separate from the default local
   `multi_agent_platform` database and from other QA passes.

6. Apply database migrations:

   ```bash
   uv run alembic upgrade head
   ```

   Expected: command completes without an error and creates or updates
   PostgreSQL tables in `multi_agent_platform_qa008`, including the
   `audit_*` tables from migration `0008_production_audit_debugging`.
