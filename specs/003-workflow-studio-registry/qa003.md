# QA Guide For Spec 003

This guide explains how to test the Phase 1, Phase 2, and Phase 3 work for Spec `003`, which is the first workflow-studio authoring slice.

It follows the same style as `qa002.md`: every step explains what you are doing, why it matters, and what success looks like.

## 1. What You Are Testing

Spec `003` currently delivers the draft-authoring foundations for the workflow registry:

- database tables and migration for workflow lineages, drafts, and immutable revisions
- workflow-registry JSON APIs for list, create, fetch, save, and editor metadata
- embedded admin HTML pages for browsing drafts and opening a draft editor
- centralized field-help metadata used by help-modal buttons in the editor
- optimistic concurrency so stale saves are rejected instead of silently overwriting newer work

This guide is intentionally scoped to the implemented phases. Validation, publish, sharing grants, and immutable version detail flows are planned for later phases and are not part of this QA run.

## 2. Before You Start

You need:

- Python `3.12`
- `uv`
- Docker with Docker Compose
- a terminal
- a browser if you want to verify the embedded HTML pages visually

## 4. Start Dependencies

Install dependencies:

```bash
uv sync
```

Start PostgreSQL:

```bash
docker compose up -d postgres
```

Apply migrations:

```bash
uv run alembic upgrade head
```

What is happening here:

- `uv sync` installs Python packages, including the template renderer used by the admin HTML pages
- `docker compose up -d postgres` starts the database the platform uses for durable workflow metadata
- `alembic upgrade head` creates the new workflow-registry tables from migration `0003_workflow_registry`

Success looks like:

- each command exits without errors
- the database now contains tables like `workflow_lineages`, `workflow_drafts`, and `workflow_draft_revisions`

## 6. Create A Tenant-Scoped Draft Through The API

Run:

```bash

  -H "X-Local-Principal: tenant-admin-acme" \
  -H "Content-Type: application/json" \
  -X POST \
  http://127.0.0.1:8000/admin/workflows \
  -d '{
    "scope_type": "tenant",
    "workflow_kind": "main_workflow",
    "slug": "customer-intake",
    "display_name": "Customer Intake",
    "document": {
      "workflow_key": "customer-intake",
      "display_name": "Customer Intake",
      "description": "Collect incoming work and route it.",
      "workflow_kind": "main_workflow",
      "entry_node_key": "triage-node",
      "roles": [
        {
          "role_key": "triage-role",
          "display_name": "Triage Role",
          "purpose": "Assess the incoming payload.",
          "input_contract_key": "intake-request",
          "output_contract_key": "triage-result",
          "skill_bindings": [
            {
              "binding_key": "triage-binding",
              "skill_slug": "triage-agent",
              "skill_version": "2026.04.1",
              "purpose": "Perform triage."
            }
          ]
        }
      ],
      "contracts": [
        {"contract_key": "intake-request", "json_schema": {"type": "object"}},
        {"contract_key": "triage-result", "json_schema": {"type": "object"}}
      ],
      "nodes": [
        {
          "node_key": "triage-node",
          "node_type": "role",
          "display_name": "Triage",
          "role_key": "triage-role"

```

What is happening here:

- the service creates a new workflow lineage
- it creates the active draft head for that lineage
- it writes revision `1` as the first immutable snapshot of the authored document
- it records audit metadata for the draft creation event

Success looks like:

- the response status is `201`
- the response includes `workflow_draft_id`
- the response includes `current_revision_number: 1`

Success looks like:

- the fetch response returns the same document you created

## 8. Save A New Draft Revision

Run:

```bash
curl \
  -H "X-Local-Principal: tenant-admin-acme" \
  -H "Content-Type: application/json" \
  -X PUT \
  http://127.0.0.1:8000/admin/workflows/drafts/<workflow_draft_id> \
  -d '{
    "base_revision_number": 1,
    "display_name": "Customer Intake Updated",
    "change_summary": "Refine the editor title",
    "document": {
      "workflow_key": "customer-intake",
      "display_name": "Customer Intake Updated",
      "description": "Collect incoming work and route it.",
      "workflow_kind": "main_workflow",
      "entry_node_key": "triage-node",
      "roles": [
        {
          "role_key": "triage-role",
          "display_name": "Triage Role",
          "purpose": "Assess the incoming payload.",
          "input_contract_key": "intake-request",
          "output_contract_key": "triage-result",
          "skill_bindings": [
            {
              "binding_key": "triage-binding",
              "skill_slug": "triage-agent",
              "skill_version": "2026.04.1",
              "purpose": "Perform triage."
            }
          ]
        }
      ],
      "contracts": [
        {"contract_key": "intake-request", "json_schema": {"type": "object"}},
        {"contract_key": "triage-result", "json_schema": {"type": "object"}}
      ],
      "nodes": [
        {
          "node_key": "triage-node",
          "node_type": "role",
          "display_name": "Triage",
          "role_key": "triage-role"
        }
      ],
      "edges": [],
      "join_policies": [],
      "approval_gates": [],
      "subworkflow_refs": []
    }
  }'
```

What is happening here:

- the service checks that the current draft head is still revision `1`
- if it matches, the service writes a new immutable revision snapshot
- the draft head moves forward to revision `2`
- the old snapshot remains durable for future lineage history

Success looks like:

- the response status is `200`
- the response includes `current_revision_number: 2`
- the display name changes to `Customer Intake Updated`

## 9. Verify Optimistic Concurrency

Repeat the same save call from Step 8, but leave `base_revision_number` set to `1`.

What is happening here:

- the request is pretending it still knows the latest draft head
- the service detects that revision `2` already exists and blocks the stale write

Success looks like:

- the response status is `409`
- the response detail says the workflow draft revision is stale

Why this matters:

- this is the core safety feature that prevents one admin session from silently overwriting another session’s more recent save

## 13. Troubleshooting

- `403` on tenant draft routes: confirm you are using `tenant-admin-acme`, not `tenant-user-acme`
- `403` on platform draft creation: confirm you are using `platform-admin`
- `409` on save: fetch the draft again and use the latest `current_revision_number`
- blank UI page or missing styles: confirm the API started after the Jinja templates and `/admin/static` mount were added
- migration errors: rerun `uv run alembic upgrade head` and verify the database is pointed at the local PostgreSQL instance from `.env.qa003`
