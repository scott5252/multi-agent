# QA Guide For Spec 003

This guide explains how to test the full Spec `003` workflow-registry flow.

It keeps the original detailed Phase 1, Phase 2, and Phase 3 walkthrough, and
adds the later Phase 4 and Phase 5 validation, publish, sharing, and successor
draft flows in the same style as `qa002.md`: every step explains what you are
doing, why it matters, and what success looks like.

## 1. What You Are Testing

Spec `003` now delivers:

- database tables and migration for workflow lineages, drafts, validations, and published versions
- workflow-registry JSON APIs for list, create, fetch, save, validate, publish, version detail, and sharing grants
- embedded admin HTML pages for browsing drafts, opening a draft editor, and viewing published version detail
- centralized field-help metadata used by help-modal buttons in the editor
- optimistic concurrency so stale saves are rejected instead of silently overwriting newer work
- validation findings for contracts, skill versions, join policies, approval gates, and subworkflow references
- immutable publish of compiled workflow version bundles
- tenant sharing grants for platform-scoped published assets
- browser-friendly local QA login for the embedded admin pages

What is happening here:

## 9. Verify Optimistic Concurrency

Repeat the same save call from Step 8, but leave `base_revision_number` set to
`1`.

What is happening here:

- the request is pretending it still knows the latest draft head
- the service detects that revision `2` already exists and blocks the stale write

Success looks like:

- the response status is `409`
- the response detail says the workflow draft revision is stale

Why this matters:

- this is the core safety feature that prevents one admin session from silently overwriting another session’s more recent save

## 28. Troubleshooting

- `401 missing local principal header or cookie`: return to `/auth/local-login` for browser flows, or add `X-Local-Principal` for `curl`
- `insert or update on table "access_decision_records" violates foreign key constraint "fk_access_decision_records_tenant_id_tenants"`: seed the `acme` tenant row in Step `4.1` before using `tenant-admin-acme`
- `403` on tenant draft routes: confirm you are using `tenant-admin-acme`, not `tenant-user-acme`
- `403` on platform draft creation, publish, or sharing grants: confirm you are using `platform-admin`
- `409` on save: fetch the draft again and use the latest `current_revision_number`
- `409 validation result is stale or failed publish readiness`: re-run validation against the latest draft revision and publish with the new `validation_result_id`
- `503 compiled bundle artifact persistence failed`: check `FILESYSTEM_STORAGE_ROOT` and confirm the app can write artifact files
- blank UI page or missing styles: confirm the API started after the Jinja templates and `/admin/static` mount were added
- migration errors: rerun `uv run alembic upgrade head` and verify the database is pointed at the local PostgreSQL instance from `.env.qa003`
