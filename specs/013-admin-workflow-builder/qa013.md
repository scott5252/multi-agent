# QA013: Guided Admin Workflow Builder

## Goal

Validate that Spec `013` lets authorized administrators create, validate,
publish, and review workflow drafts through the guided admin builder without
editing raw JSON as the primary workflow. The checks cover local-principal
authentication, tenant and platform scope handling, editor metadata, reference
lookups, graph preview, field-level validation, stale-save conflicts,
revision history, copy and restore controls, publish-gate blocking reasons,
immutable bundle publication, safe version detail evidence, documentation, and
automated quality gates.

This guide is written for non-developer reviewers. It gives copy and paste
commands, stores API responses under `/tmp/qa013-*`, and explains what each
result proves. Keep Terminal B open for the whole pass so exported shell
variables remain available.

## What This Guide Covers

Use this as the standalone reviewer checklist for Spec `013`. It validates:

- Local QA environment setup with deterministic Acme and Globex tenants.
- Authentication with local principals for platform admin, tenant admin, and
  same-tenant read-only reviewer roles.
- Clean PostgreSQL setup from scratch in `multi_agent_platform_qa013`.
- Admin registry list, create page, editor page, revision page, publish gate
  page, and version detail page availability.
- Typed editor metadata for sections, fields, lookup sources, action URLs,
  capabilities, and validation code mapping.
- Tenant-filtered lookup and graph preview JSON endpoints.
- Guided draft create and save using structured builder sections.
- Validation findings with stable `section_key`, `field_path`,
  `graph_element_id`, remediation, and blocking flags.
- Reference readiness for prompt/profile, skill, subworkflow, and required
  test evidence without raw prompts, secrets, credentials, or provider payloads.
- Stale save conflict behavior that returns `409` and does not create an
  extra revision.
- Revision list, copy draft, and restore revision behavior.
- Publish gate behavior for blocked, stale, unauthorized, and ready states.
- Published immutable bundle evidence with source revision, publish gate
  digest, pin summaries, graph summary, and test evidence.
- Required reviewer evidence: Ruff, format, mypy, focused Spec 013 tests, and
  full coverage gate.

Important current-implementation note: the builder implementation is additive
on top of the existing workflow registry tables and services. The manual flow
uses typed JSON endpoints for deterministic setup and then verifies that the
server-rendered pages expose the corresponding guided surfaces. The reference
readiness checks currently use safe references stored in the builder document
and visible subworkflow identifiers; deeper prompt library, profile service,
provider catalog, and test bench checks can plug into the same response
contracts without changing this guide. Audit evidence is stored through the
existing registry service flow and uses safe summaries only.

## How To Use This Guide

You need two terminal windows:

- Terminal A runs the API server and should stay open.
- Terminal B runs setup, `curl`, `jq`, SQL verification, and quality checks.

Run the sections in order. Commands write responses into `/tmp/qa013-*.json`,
`/tmp/qa013-*.html`, or `/tmp/qa013-*.txt`. If a command prints `null`, an
empty value, or a status different from the stated expectation, stop and
inspect the saved file before continuing.

What the most important terms mean:

- A **builder document** is the structured workflow draft body with metadata,
  roles, prompt/profile references, skills, contracts, graph nodes, graph
  edges, joins, approvals, subworkflows, tests, and editor annotations.
- A **graph preview** is the server-derived node and edge projection used by
  the UI and validation panel.
- A **reference readiness snapshot** is a safe summary of whether a referenced
  prompt/profile, skill, subworkflow, or test result is publish-ready.
- A **publish gate** is the final readiness decision that ties the current
  draft revision, validation result, reference pins, and required tests to a
  deterministic digest.
- A **safe summary** must not include raw prompts, raw secret values,
  credential values, provider payloads, or unauthorized tenant details.

## Environment

Run all commands in this section from the repository root.

1. Copy the QA environment file into the app's `.env`:

   ```bash
   cp specs/013-admin-workflow-builder/.env.qa013 .env
   ```

   Expected: no output. The app now uses local-principal auth and the
   PostgreSQL QA database `multi_agent_platform_qa013` on `127.0.0.1:5432`.

   What this proves: the manual QA run is isolated from the default developer
   database and from other Spec Kit QA passes.

2. Confirm `curl` and `jq` are available:

   ```bash
   curl --version | head -1
   jq --version
   ```

   Expected: each command prints a version.

   What this proves: Terminal B can call the API and extract response ids.

3. Remove old QA013 files:

   ```bash
   find /tmp -type f \( -name 'qa013-*.json' -o -name 'qa013-*.html' -o -name 'qa013-*.txt' \) -exec rm -f {} +
   ```

   Expected: no output.

   What this proves: later redaction and response checks use fresh evidence.

4. Install dependencies:

   ```bash
   uv sync
   ```

   Expected: command completes without an error.

   What this proves: the same dependency set used by automated tests is
   installed for the reviewer pass.

5. Start PostgreSQL:

   ```bash
   docker compose up -d postgres
   ```

   Expected: Docker reports the PostgreSQL service is running.

   What this proves: the local database dependency is available.

6. Create the QA013 database if needed:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -U postgres -d postgres -tc "SELECT 1 FROM pg_database WHERE datname = '\''multi_agent_platform_qa013'\''" | grep -q 1 || createdb -U postgres multi_agent_platform_qa013'
   ```

   Expected: no output.

   What this proves: QA013 data is stored in its own database.

7. Apply database migrations:

   ```bash
   uv run alembic upgrade head
   ```

   Expected: command completes without an error.

   What this proves: workflow registry, audit, prompt/profile, provider, and
   reliability tables are present before the builder flow runs.

8. Seed deterministic tenants:

   ```bash
   docker compose exec -T postgres psql -U postgres -d multi_agent_platform_qa013 -v ON_ERROR_STOP=1 <<'SQL'
   INSERT INTO tenants (
     tenant_id, slug, display_name, status, created_at, updated_at
   ) VALUES
     ('11111111-1111-1111-1111-111111111111', 'acme', 'Acme', 'active', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP),
     ('22222222-2222-2222-2222-222222222222', 'globex', 'Globex', 'active', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP)
   ON CONFLICT (tenant_id) DO UPDATE SET
     slug = EXCLUDED.slug,
     display_name = EXCLUDED.display_name,
     status = EXCLUDED.status,
     updated_at = CURRENT_TIMESTAMP;
   SQL
   ```

   Expected: PostgreSQL prints `INSERT 0 2` or an equivalent upsert result.

   What this proves: local principals can exercise tenant-scoped builder
   behavior deterministically.

9. Start the API in Terminal A:

   ```bash
   uv run uvicorn multi_agent_platform.api.main:app --reload
   ```

   Expected: the server listens on `http://127.0.0.1:8000`.

   What this proves: the browser and API checks can use the same app process.

## Troubleshooting

- If `curl` cannot connect, confirm Terminal A is still running the API and
  that `.env` was copied from `.env.qa013` before the server started.
- If local principal requests return `401`, verify `AUTH_MODE=local_principal`
  and the `X-Local-Principal` header value in Terminal B.
- If PostgreSQL commands fail, run `docker compose ps postgres` and confirm
  the service is healthy.
- If migration errors mention an old schema, recreate only the QA database
  `multi_agent_platform_qa013` and rerun migrations.
- If draft creation returns `409`, change the slug suffix or remove prior
  QA013 draft rows from the isolated QA database.
- If stale save returns `200`, verify the first save advanced the revision and
  that the stale payload still contains `base_revision_number: 1`.
- If publish gate is blocked for the ready draft, inspect
  `/tmp/qa013-validation-ready.json` and resolve any blocking validation
  finding before retrying the gate.
- If the safe evidence scan prints a value, inspect the matching response file
  and confirm whether the value is a harmless placeholder or an unsafe field.
