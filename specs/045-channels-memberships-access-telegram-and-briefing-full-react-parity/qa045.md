# QA045: Channels, Memberships, Access, Telegram, And Briefing Full React Parity

## Goal

QA045 proves that memberships, access administration, Telegram configuration,
channel diagnostics, and briefing preferences are React-only browser workflows.

Old Jinja URLs should redirect to `/admin/app/memberships` or
`/admin/app/channels`; retained JSON APIs should keep serving React; raw tokens,
Telegram identifiers, private messages, Auth0 subjects, emails, and preference
payloads should stay redacted.

What this proves: people and channel administration can complete the React UI2
migration without widening tenant access or reviving the deleted Jinja pages.

## What This Guide Covers

This guide covers these Spec 045 checks.

1. Old `/admin/memberships` browser links redirect to React memberships.
2. Old membership form-post routes execute retained services and redirect.
3. Old `/admin/telegram` browser links redirect to React channels.
4. Old Telegram form-post routes execute retained services and redirect.
5. Old Telegram link-token form posts return a one-time JSON token response.
6. Old `/admin/briefing-preferences` browser links redirect to React channels.
7. Old briefing save/import/export browser routes redirect or return safe JSON.
8. Retained `/api/*` contracts still serve React and API callers.
9. Deleted templates remain absent and unreferenced.
10. Local-principal and Auth0-shaped test coverage remains intact.

## Troubleshooting

If local login fails, open
`http://127.0.0.1:8000/auth/local-login?redirect_to=/admin/app/channels` and
choose `platform-admin`.

Expected: the browser lands on the React channels workspace.

If a deleted template path appears in an error, run the retirement scanner test
and stop until the runtime reference is removed.

Expected: only the scanner test names deleted template files.

If link-token tests fail, remember that the raw token may appear only in the
immediate create response.

Expected: token list, diagnostics, screenshots, logs, and exports show
fingerprints or metadata only.

If briefing validation errors are returned, they should be safe JSON problem
details rather than rendered Jinja pages.

Expected: no stack trace or template content appears in validation failures.
