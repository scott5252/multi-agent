# QA014: Skill Registry Lifecycle Browser Workflows

## Goal

Validate that Spec 014 V2 lets platform admins and tenant admins complete the
governed skill registry lifecycle from server-rendered browser pages while the
JSON APIs remain available for automation and diagnostics. The checks cover
package creation, manifest candidate parsing, validation, immutable
publication, tenant grants, tenant discovery, installation, credential
reference configuration, smoke-test readiness, binding eligibility preview,
stale revision rejection, tenant isolation, redaction, documentation, and
automated quality evidence.

This guide is written for reviewers who want copy/paste commands and clear
expected results. The companion `qa014_ui.md` is the browser-first walkthrough.
This file adds setup, diagnostics, API smoke checks, redaction scans, and
quality commands that preserve evidence under `/tmp/qa014-*`.

## What This Guide Covers

- Local QA environment setup with `multi_agent_platform_qa014`.
- Local-principal auth for `platform-admin`, `tenant-admin-acme`,
  `tenant-admin-globex`, and `tenant-operator-acme`.
- Deterministic Acme and Globex tenants.
- Server-rendered routes under `/admin/skill-registry/ui`.
- Existing JSON routes under `/admin/skill-registry` for diagnostics.
- Browser-form contracts for package, candidate, grant, install, credential,
  smoke-test, and eligibility actions.
- Screenshot evidence under `output/playwright/qa014_ui`.
- Tenant isolation between Acme and Globex.
- Redaction of raw manifests, raw credentials, provider tokens, unsafe docs,
  raw smoke-test logs, and cross-tenant data.
- Focused tests, docs tests, linting, typing, and the full coverage gate.

Current implementation note: the V2 slice uses the existing in-memory
`SkillRegistryService` wrapper for the server-rendered admin paths in tests.
The durable database schema from Spec 014 remains the target for production
storage, and the V2 UI layer is additive. Browser workflows are covered by
integration tests and screenshot-backed QA evidence; smoke-test execution is
represented through safe readiness state rather than synchronous external tool
execution.

## How To Use This Guide

Use two terminals from the repository root.

- Terminal A runs the API server and stays open.
- Terminal B runs setup, diagnostics, evidence capture, and quality commands.

Run the sections in order. Keep Terminal B open because several commands write
files under `/tmp/qa014-*` for later evidence review.

Important terms:

- A skill package is the lineage root owned by platform admins.
- A manifest candidate is pasted or uploaded YAML/JSON that has not yet become
  an immutable published version.
- A tenant grant lets a tenant discover and install a published version.
- An installation pins a tenant to an exact package version.
- A revision token rejects stale browser submissions.
- A safe summary is the only kind of candidate, credential, fixture, policy, or
  smoke-test data that should appear in HTML or screenshots.

## Troubleshooting

- If local login returns unauthorized, confirm `.env` was copied from
  `.env.qa014` and restart the API.
- If database setup fails, confirm Docker is running and the `postgres`
  service is healthy.
- If browser pages show no principals, inspect `LOCAL_PRINCIPAL_CATALOG_JSON`
  for valid JSON.
- If Acme cannot see a version, confirm the platform grant step completed in
  the browser.
- If a stale conflict does not appear, open two tabs before submitting the
  first change and reuse the older revision token in the second tab.
- If redaction scan fails, inspect the matching `/tmp/qa014-*` file and verify
  whether the unsafe string came from test data, page source, or a reviewer
  note.
- If the focused tests pass but the full coverage gate fails, run the full
  command locally and inspect the coverage table for unrelated regressions.
