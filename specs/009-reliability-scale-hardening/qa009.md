# QA009: Reliability And Scale Hardening

## Goal

Validate that Spec `009` adds the reliability and scale-hardening foundation
needed for tenant-aware admission control, quotas, fair scheduling, worker
recovery safety, retry budgets, circuit breakers, compensation, dead letters,
artifact-throughput limits, operational inspection, documentation, and review
evidence.

This guide is written for non-developers. It gives copy/paste commands,
explains what each command proves, and calls out current implementation limits
so reviewers can distinguish a real failure from a feature slice that is
present but not yet connected to live workflow execution end to end.

## What This Guide Covers

Use this as a standalone reviewer checklist for Spec `009`. It validates:

- Local QA environment setup with deterministic Acme and Globex tenants.
- Clean PostgreSQL setup from scratch in `multi_agent_platform_qa009`.
- Reliability migration `0009_reliability_scale_hardening`.
- Seeded reliability records for policies, admission decisions, quota
  counters, fairness windows, capacity snapshots, scaling decisions, retries,
  circuit breakers, compensation requests, dead letters, control changes,
  artifact throughput, and failure injection points.
- Manual SQL inspection for backpressure outcomes, tenant quotas, fairness
  debt, retry stop reasons, breaker transitions, compensation outcomes,
  dead-letter next actions, metadata-only artifact evidence, and failure
  injection coverage.
- Manual API smoke checks for `/admin/reliability/*` routes and reliability UI
  templates.
- Automated tests for admission, quotas, fairness, autoscaling, pooling,
  leases, stale fencing tokens, side-effect safety, retries, breakers,
  compensation, dead letters, repository boundaries, API schemas, docs, and
  deterministic performance profiles.
- Required reviewer evidence: Ruff, format, mypy, focused Spec 009 tests, and
  the full coverage gate.

Important current-implementation note: this QA guide validates the Spec `009`
implementation currently present in this repository. The code includes durable
reliability tables, domain state-machine logic, settings, metrics/logging/audit
helpers, storage-throughput controls, API schemas, registered FastAPI routes,
minimal admin UI templates, docs, and tests. The public reliability list
endpoints are currently route and response-shape smoke handlers; they return
empty `items` arrays and do not yet read the seeded PostgreSQL reliability
records. The detailed operational state is therefore verified with SQL queries
against the seeded reliability tables and with automated unit, contract,
integration, and performance tests. Authorization helper behavior is covered by
unit tests; the reliability API router itself does not yet enforce local
principal roles. Performance tests are deterministic pytest profiles, not a
distributed load-test service.

## How To Use This Guide

You need two terminal windows:

- Terminal A runs the API server and should stay open for the manual API and
  UI checks.
- Terminal B runs setup, seed SQL, `curl`, `jq`, SQL verification, and quality
  commands from the repository root.

Run the sections in order. The commands save responses into
`/tmp/qa009-*.json`, `/tmp/qa009-*.html`, or `/tmp/qa009-*.txt` files. Keep
using the same Terminal B session so shell variables such as `$ACME_TENANT_ID`
remain available.

If a command prints `null`, an empty value where the instructions say a value
is expected, or an HTTP status different from the expected status, stop and
inspect the saved `/tmp/qa009-*` file before continuing.

What the most important terms mean:

- **Admission** decides whether submitted work is accepted, queued, delayed,
  throttled, rejected, or retry-eligible.
- **Backpressure** is the intentional queueing, delay, throttle, or rejection
  of work before shared capacity is exhausted.
- **Tenant quota** is a tenant-scoped limit for submitted work, active work,
  retries, recovery, compensation, artifacts, or operational actions.
- **Fairness debt** means a tenant should receive future preference because it
  received less than its weighted share. **Burst debt** means a tenant borrowed
  extra capacity and should receive lower future priority until the debt is
  repaid.
- **Worker lease fencing** means every recovered worker write must include the
  current lease id and claim attempt, so stale workers cannot overwrite
  recovered work.
- **Circuit breaker** is a protective control that blocks unsafe traffic to a
  failing dependency or operation until cooldown and probe evidence permit
  limited traffic again.
- **Compensation** is cleanup, reversal, reconciliation, or manual follow-up
  for an external side effect.
- **Dead letter** is an inspectable stop point for work that automated recovery
  cannot safely continue.
- **Metadata-only artifact evidence** means PostgreSQL stores artifact refs,
  checksums, status, and audit metadata, not large replay/export payloads.

## Environment

Run these setup steps from the repository root.

1. Copy the QA environment file into the app's `.env`:

   ```bash
   cp specs/009-reliability-scale-hardening/.env.qa009 .env
   ```

   Expected: no output. This makes the app use local-principal auth and the
   PostgreSQL QA database `multi_agent_platform_qa009` on `127.0.0.1:5432`.

2. Confirm `curl` and `jq` are installed:

   ```bash
   curl --version | head -1
   jq --version
   ```

   Expected: each command prints a version. If `jq` is unavailable, you can
   still run the API calls and inspect the saved JSON files manually.

3. Remove old QA009 response files from prior attempts:

   ```bash
   find /tmp -type f \( -name 'qa009-*.json' -o -name 'qa009-*.html' -o -name 'qa009-*.txt' \) -exec rm -f {} +
   ```

   Expected: no output. This prevents later checks, especially response
   review, from reading stale files from an earlier run.

4. Install dependencies:

   ```bash
   uv sync
   ```

   Expected: command completes without an error.

5. Start PostgreSQL:

   ```bash
   docker compose up -d postgres
   ```

   Expected: Docker starts the local `postgres:16-alpine` service. If it was
   already running, Docker reports that it is up to date.

6. Create the dedicated QA009 PostgreSQL database if it does not already
   exist:

   ```bash
   docker compose exec -T postgres sh -c \
     'psql -U postgres -d postgres -tc "SELECT 1 FROM pg_database WHERE datname = '\''multi_agent_platform_qa009'\''" | grep -q 1 || createdb -U postgres multi_agent_platform_qa009'
   ```

   Expected: no output. This keeps QA009 data separate from the default local
   database and from other QA passes.

7. Apply database migrations:

   ```bash
   uv run alembic upgrade head
   ```

   Expected: command completes without an error and creates or updates
   PostgreSQL tables in `multi_agent_platform_qa009`, including all tables
   whose names start with `reliability_`.

8. Confirm the reliability migration tables exist:

   ```bash
   docker compose exec -T postgres psql -U postgres -d multi_agent_platform_qa009 -c \
     "SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' AND table_name LIKE 'reliability_%' ORDER BY table_name;"
   ```

   Expected: the output includes these tables:
   `reliability_admission_decisions`,
   `reliability_artifact_throughput_windows`,
   `reliability_capacity_snapshots`,
   `reliability_circuit_breaker_events`,
   `reliability_circuit_breakers`,
   `reliability_compensation_requests`,
   `reliability_dead_letters`,
   `reliability_failure_injection_records`,
   `reliability_fairness_windows`,
   `reliability_operational_control_changes`,
   `reliability_policies`,
   `reliability_retry_schedules`,
   `reliability_tenant_quota_counters`, and
   `reliability_worker_pool_scaling_decisions`.
