# QA015: Agent And Workflow Test Bench

## Goal

Validate that Spec 015 lets platform and tenant admins define reusable agent
and workflow test suites, add fixture-backed cases, run safe deterministic
test executions, inspect redacted result diagnostics, and evaluate workflow
publication gates without production credentials or real external side
effects.

This guide is for reviewers who want copy and paste commands plus expected
results. The companion `qa015_ui.md` is the browser-first walkthrough. This
file adds environment setup, API checks, redaction checks, tenant isolation
checks, automated evidence commands, and quality gates for the full QA pass.

## What This Guide Covers

- Local setup for `multi_agent_platform_qa015`.
- Local-principal login for platform, Acme, Globex, operator, and auditor
  personas.
- Admin UI pages under `/admin/agent-tests/ui`.
- JSON API routes under `/admin/agent-tests`.
- Suite creation for workflow drafts and other target types.
- Case creation with fixture summaries, expected contract shapes, and
  assertions.
- Mock model, mock tools, and mocked real-gateway safe execution modes.
- Approved real probe rejection when approval metadata is missing.
- Run detail diagnostics with model/provider, token, latency, contract,
  assertion, side-effect, redaction, and artifact summaries.
- Publish gate evaluation for required suites and current target versions.
- Tenant isolation between Acme and Globex.
- Redaction of fake secret-looking values in fixtures and transcripts.
- Docs validation, linting, typing, and the repository coverage gate.

Current implementation note: the first QA015 slice executes deterministic
test-bench runs synchronously through the sandbox service. It records durable
suite, case, assertion, run, and run-step metadata in PostgreSQL, while large
or sensitive evidence is represented by safe summaries and artifact references.
The approved real dependency mode remains blocked unless explicit approval
metadata is provided; this QA guide uses mock and mocked-provider paths only.

## How To Use This Guide

Use two terminals from the repository root.

- Terminal A runs the API server and stays open.
- Terminal B runs setup, API checks, redaction scans, and quality commands.

Keep all generated evidence under `/tmp/qa015-*`,
`.data/qa015-artifacts`, or `output/playwright/qa015_ui`. If a command writes
to another location, stop and review the command before continuing.

Important terms:

- A suite is a tenant-scoped collection of cases for one target.
- A case is one fixture, expected contract shape, and assertion list.
- A safe mode controls whether model and tool execution is mocked, blocked, or
  explicitly approved.
- A run is the durable test execution result for a suite and target version.
- A publish gate summary is ready only when required suites have current
  passing evidence.
- A redacted summary is the only evidence reviewers should see inline.

5. Create an Acme workflow-draft suite:

   ```bash
   curl --fail --silent -X POST "$QA015_BASE_URL/admin/agent-tests/suites" \
     -H "$QA015_PLATFORM_HEADER" \
     -H "Content-Type: application/json" \
     -d '{
       "tenant_id":"11111111-1111-1111-1111-111111111111",
       "name":"QA015 Draft Workflow Guard",
       "target_type":"workflow_draft",
       "target_id":"qa015-draft-triage",
       "target_version":"draft-rev-1",

       "required_for_publish":true
     }' | tee /tmp/qa015-suite.json
   ```

   Expected: the response contains `suite_id`, `workflow_draft`, and
   `required_for_publish`.

   What this proves: a platform admin can create tenant-scoped test suites.

6. Capture the suite id:

   ```bash
   export QA015_SUITE_ID="$(jq -r '.suite_id' /tmp/qa015-suite.json)"
   test -n "$QA015_SUITE_ID"
   ```

   Expected: no output.

   What this proves: later checks target the created suite.

7. Add a fixture-backed passing case:

   ```bash
   curl --fail --silent -X POST "$QA015_BASE_URL/admin/agent-tests/suites/$QA015_SUITE_ID/cases" \
     -H "$QA015_ACME_HEADER" \
     -H "Content-Type: application/json" \
     -d '{
       "name":"Passing intake case",
       "fixture":{"request":"summarize intake","api_key":"qa015-fake-value"},
       "expected_contract_shape":{"status":{},"contract":{}},
       "assertions":[
         {"kind":"deterministic","path":"status","comparator":"equals","expected_value":"passed"},
         {"kind":"deterministic","path":"contract.summary","comparator":"contains","expected_value":"intake"}
       ]
     }' | tee /tmp/qa015-case.json
   ```

   Expected: fixture preview redacts `api_key`.

   What this proves: case creation stores safe fixture summaries and assertion
   definitions.

8. Run the suite with the mock model:

   ```bash
   curl --fail --silent -X POST "$QA015_BASE_URL/admin/agent-tests/suites/$QA015_SUITE_ID/runs" \
     -H "$QA015_ACME_HEADER" \
     -H "Content-Type: application/json" \
     -d '{"safe_mode":"mock_model","target_version":"draft-rev-1","idempotency_key":"qa015-mock-run"}' \
     | tee /tmp/qa015-run-mock.json
   ```

   Expected: the run status is `passed`.

   What this proves: deterministic mock execution evaluates assertions and
   stores run evidence.

9. Run the suite with real model mode and side effects disabled:

   ```bash
   curl --fail --silent -X POST "$QA015_BASE_URL/admin/agent-tests/suites/$QA015_SUITE_ID/runs" \
     -H "$QA015_ACME_HEADER" \
     -H "Content-Type: application/json" \
     -d '{"safe_mode":"real_model_side_effects_disabled","target_version":"draft-rev-1","idempotency_key":"qa015-mocked-gateway-run"}' \
     | tee /tmp/qa015-run-mocked-gateway.json
   ```

   Expected: the run status is `passed`, the model provider is
   `mocked-gateway`, and `blocked_side_effect_count` is at least one.

   What this proves: mocked provider execution records model metadata while
   blocking external side effects.

10. Verify approved probe rejection without approval metadata:

    ```bash
    curl --silent --output /tmp/qa015-approved-probe-rejected.json --write-out '%{http_code}\n' \
      -X POST "$QA015_BASE_URL/admin/agent-tests/suites/$QA015_SUITE_ID/runs" \
      -H "$QA015_ACME_HEADER" \
      -H "Content-Type: application/json" \
      -d '{"safe_mode":"approved_real_probe","target_version":"draft-rev-1"}'
    ```

    Expected: the status code is `400`.

    What this proves: real dependency probes fail closed unless approval
    metadata is supplied.

    Expected: the gate status is `ready`.

    What this proves: current passing evidence satisfies the required suite

    curl --fail --silent -X POST "$QA015_BASE_URL/admin/agent-tests/publish-gates/evaluate" \

## Troubleshooting

- If login does not show local-principal cards, confirm `.env` was copied from
  `.env.qa015` and restart the API.
- If API routes return unauthorized, confirm `X-Local-Principal` is spelled
  exactly and the principal key exists in `LOCAL_PRINCIPAL_CATALOG_JSON`.
- If the suite create call says `tenant_id` is missing, confirm the request
  body includes the Acme tenant id.
- If Globex can read an Acme suite, stop validation and inspect tenant access
  policy before continuing.
- If the publish gate is blocked for `draft-rev-1`, confirm the suite was
  created with `required_for_publish` set to true and that a passing run exists
  for the same target version.
- If the approved probe request succeeds without approval metadata, stop
  validation because real dependency safety is not fail-closed.
- If raw fake credential values appear in saved evidence, stop validation and
  inspect redaction before continuing.
- If Playwright cannot start the API, check `/tmp/qa015-api.log`.
- If the worker exits, check `/tmp/qa015-worker.log`; deterministic bench runs
  can still be validated through the API server.
- If the docs validator fails line counts, inspect `qa015.md`,
  `qa015_ui.md`, and `.env.qa015` for accidental truncation.
- If full coverage fails only because global historical coverage changed,
  include the terminal output in the validation notes and keep focused QA015
  tests visible.
