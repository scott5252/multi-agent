# QA Guide For Specs 001 And 002

This guide explains how to test the platform foundation from Spec `001` and the authentication and authorization work from Spec `002`.

It is written for both technical and non-technical testers. Every step explains:

- what the command is doing
- why the step matters
- what values you should use
- what success looks like

If you are not comfortable with code, that is okay. You can still follow this guide step by step and compare what you see to the expected results.

## 1. What You Are Testing

### Spec 001: Platform Foundation

Spec `001` created the base platform that everything else depends on:

- project setup
- database migrations
- API startup
- worker startup
- health and readiness endpoints
- storage and secret-provider foundations
- tenant-scope safety checks
- automated quality gates

In simple terms, Spec `001` makes sure the application can start correctly, talk to its database, report whether it is healthy, and enforce the basic platform rules.

### Spec 002: Authentication And Authorization

Spec `002` added the security layer:

- local test identities using `AUTH_MODE=local_principal`
- production-style Auth0 mode using `AUTH_MODE=auth0`
- endpoint `/auth/me`
- endpoint `/auth/tenant-context/{tenant_id}`
- tenant user, tenant admin, and platform admin role separation
- role-grant administration
- support override request and approval flow
- access-decision auditing
- delegated credential and secret-boundary protection

In simple terms, Spec `002` makes sure the right person can do the right thing, at the right tenant, and that every allow or deny decision can be reviewed later.

## 3. Important Values Used In This Guide

These values appear many times in the testing steps. They are not random placeholders. They represent the exact test data this guide expects.

### Main URL

- `BASE_URL=http://127.0.0.1:8000`

This means the API is expected to be running on your own machine on port `8000`.

### Main Tenant

- `TENANT_ID=11111111-1111-1111-1111-111111111111`
- tenant name: `Acme`
- tenant slug: `acme`

This is the primary tenant used for successful tenant-scoped tests.

### Other Tenant

- `OTHER_TENANT_ID=22222222-2222-2222-2222-222222222222`
- tenant name: `Globex`
- tenant slug: `globex`

This second tenant is used for negative tests. It helps prove that the platform blocks cross-tenant access.

### Local Test Users

These are the exact principal names used throughout this guide:

- `tenant-user-acme`
- `tenant-admin-acme`
- `platform-admin-a`
- `platform-admin-b`

Their meanings:

- `tenant-user-acme`: a normal user inside the `Acme` tenant
- `tenant-admin-acme`: an administrator inside the `Acme` tenant
- `platform-admin-a`: a platform-wide admin used to request support access
- `platform-admin-b`: a second platform-wide admin used to approve support access

### Why Two Platform Admins Are Needed

The support override flow intentionally requires one person to request access and a different person to approve it. This protects against a single administrator quietly granting themselves tenant access.

## 4. Recommended Test Order

Follow the steps in this order:

1. Set up the environment.
2. Start the database, API, and worker.
3. Run the Spec `001` validation steps.
4. Seed the test tenant data for Spec `002`.
5. Run the local-principal security checks.
6. Run the automated tests.
7. Run the optional Auth0 checks if needed.

This order matters because the later steps depend on the earlier setup being correct.

## 8. Spec 002 Manual Validation In Local-Principal Mode

### 8.1 Validate `/auth/me`

Run as tenant user:

```bash
curl -i -H "X-Local-Principal: tenant-user-acme" "$BASE_URL/auth/me"
```

Run as tenant admin:

```bash
curl -i -H "X-Local-Principal: tenant-admin-acme" "$BASE_URL/auth/me"
```

Run as platform admin:

```bash
curl -i -H "X-Local-Principal: platform-admin-a" "$BASE_URL/auth/me"
```

What this endpoint does:

- returns the identity the API believes is making the request

Why this matters:

- it proves the authentication layer is reading the local principal correctly
- it also lets you visually confirm the role and tenant context before running more advanced tests

What to look for:

- tenant user response should include `tenant_id` equal to `11111111-1111-1111-1111-111111111111`
- tenant admin response should include the same tenant ID
- platform admin response should usually not be tied to a tenant by default
- all three responses should show `auth_mode` as `local_principal`

Negative test:

```bash
curl -i "$BASE_URL/auth/me"
```

Why this matters:

- it proves the API does not silently allow requests with no identity

Success looks like:

- HTTP `401`

### 8.2 Validate `/auth/tenant-context/{tenant_id}`

Run a valid same-tenant request:

```bash
curl -i \
  -H "X-Local-Principal: tenant-user-acme" \
  "$BASE_URL/auth/tenant-context/$TENANT_ID"
```

Run an invalid cross-tenant request:

```bash
curl -i \
  -H "X-Local-Principal: tenant-user-acme" \
  "$BASE_URL/auth/tenant-context/$OTHER_TENANT_ID"
```

What this endpoint does:

- asks the API to resolve identity and authorization in the context of a specific tenant

Why this matters:

- tenant-aware authorization is one of the most important security rules in the system

Success looks like:

- same-tenant request returns HTTP `200`
- cross-tenant request returns HTTP `403`

What those results mean:

- `200` means the user is allowed inside their own tenant
- `403` means the user is known, but not allowed to do that action for that tenant

### 8.3 Prove a tenant user cannot access tenant-admin surfaces

Run:

```bash
curl -i \
  -H "X-Local-Principal: tenant-user-acme" \
  "$BASE_URL/admin/tenants/$TENANT_ID/role-grants"
```

What this command does:

- tries to call a tenant-admin endpoint as a normal tenant user

Why this matters:

- it proves that role boundaries are real, not just labels

Success looks like:

- HTTP `403`

### 8.4 Create a role grant as a platform admin

Take the real `principal_identity_id` value you copied for `tenant-user-acme` in section `7.3`. Replace the sample value below with that exact ID.

Example only:

- if your lookup showed `9f0af54b-1234-5678-9012-abcdefabcdef`, use that full value

Run:

```bash
curl -i \
  -X POST "$BASE_URL/admin/role-grants" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-a" \
  -d '{
    "principal_identity_id": "REPLACE_WITH_REAL_TENANT_USER_PRINCIPAL_ID",
    "scope_type": "tenant",
    "tenant_id": "11111111-1111-1111-1111-111111111111",
    "role_code": "tenant_user"
  }'
```

What this command does:

- asks the platform-admin route to create or update a role assignment

What the request body values mean:

- `principal_identity_id`: the internal database ID of the person receiving the role
- `scope_type: "tenant"`: the role is only for one tenant, not the entire platform
- `tenant_id`: the tenant where the role applies; here it is the `Acme` tenant
- `role_code: "tenant_user"`: the role being granted

Why this matters:

- it proves that platform-wide admins can manage role grants

Success looks like:

- HTTP `201`
- the response includes a `role_grant_id`
- the `status` is `active`

Negative test:

```bash
curl -i \
  -X POST "$BASE_URL/admin/role-grants" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: tenant-admin-acme" \
  -d '{
    "principal_identity_id": "REPLACE_WITH_REAL_TENANT_USER_PRINCIPAL_ID",
    "scope_type": "tenant",
    "tenant_id": "11111111-1111-1111-1111-111111111111",
    "role_code": "tenant_user"
  }'
```

Why this matters:

- it proves that a tenant admin does not get platform-admin powers

Success looks like:

- HTTP `403`

### 8.6 Validate support override request, approval, and use

First, prove that a platform admin is blocked from direct tenant-specific access:

```bash
curl -i \
  -H "X-Local-Principal: platform-admin-a" \
  "$BASE_URL/admin/tenants/$TENANT_ID/role-grants"
```

Why this matters:

- platform admins are intentionally separated from tenant-scoped admin actions unless an explicit support override is approved

Success looks like:

- HTTP `403`

Now create the support override request:

```bash
curl -i \
  -X POST "$BASE_URL/admin/support-overrides" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-a" \
  -d '{
    "tenant_id": "11111111-1111-1111-1111-111111111111",
    "justification": "Investigate tenant-specific support issue",
    "idempotency_key": "qa002-override-1"
  }'
```

What the request body means:

- `tenant_id`: the tenant the admin is asking to support; use the exact `Acme` tenant ID
- `justification`: the human explanation for why this special access is needed
- `idempotency_key`: a unique label for this request so that if the same request is accidentally submitted twice, the system can recognize it

Why this matters:

- the support override path is the controlled way to cross the normal tenant boundary

Success looks like:

- HTTP `201`
- the response status is `pending`

Important:

- copy the returned `support_override_request_id`
- if you repeat the test later, use a new `idempotency_key`, such as `qa002-override-2`

Now try to self-approve using the same admin:

```bash
curl -i \
  -X POST "$BASE_URL/admin/support-overrides/REPLACE_WITH_REAL_SUPPORT_OVERRIDE_REQUEST_ID/approve" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-a" \
  -d '{"expires_in_hours": 1}'
```

What `expires_in_hours: 1` means:

- the temporary support access should expire after 1 hour

Why this matters:

- this test proves one admin cannot request and approve their own exceptional access

Success looks like:

- HTTP `403`

Now approve using the second platform admin:

```bash
curl -i \
  -X POST "$BASE_URL/admin/support-overrides/REPLACE_WITH_REAL_SUPPORT_OVERRIDE_REQUEST_ID/approve" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-b" \
  -d '{"expires_in_hours": 1}'
```

Why this matters:

- this is the required two-person approval control

Success looks like:

- HTTP `200`
- status becomes `approved`
- the response includes an approver ID and expiration time

Now retry the tenant-specific access as `platform-admin-a`:

```bash
curl -i \
  -H "X-Local-Principal: platform-admin-a" \
  "$BASE_URL/admin/tenants/$TENANT_ID/role-grants"
```

Why this matters:

- this confirms the override only works after the second approver acts

Success looks like:

- HTTP `200`

### 8.7 Validate access-decision audit records

Run:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform -c \
"SELECT decision, reason_code, surface_key, tenant_id, support_override_request_id, delegated_credential_link_id, secret_free, occurred_at FROM access_decision_records ORDER BY occurred_at DESC LIMIT 20;"
```

Optional second query:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform -c \
"SELECT actor_id, action, entity_type, payload_redacted, occurred_at FROM audit_events ORDER BY occurred_at DESC LIMIT 20;"
```

What these commands do:

- read the stored audit trail created by the previous allow and deny decisions

Why this matters:

- Spec `002` requires every important access decision to be reviewable later

What to look for:

- both `allow` and `deny` rows
- `reason_code` values explaining why access was allowed or denied
- a `support_override_request_id` on the approved support case
- `secret_free` should be `true`

What `secret_free=true` means:

- the system recorded the decision without storing raw secrets or token contents in the audit record

## 13. Troubleshooting

### `503` from `/health/ready`

This usually means:

- PostgreSQL is not running
- migrations are not at the latest version
- auth configuration is invalid for the selected mode

### `401` from `/auth/me` in local-principal mode

This usually means:

- the `X-Local-Principal` header is missing
- the header value does not exactly match one of these four configured subjects:
  - `tenant-user-acme`
  - `tenant-admin-acme`
  - `platform-admin-a`
  - `platform-admin-b`

### `403` on an admin route

This usually means:

- you used the wrong role for the action
- you used the wrong tenant ID
- the support override has not yet been approved

### SQL insert errors while seeding tenants

This usually means:

- the raw SQL is missing required database columns
- the tenant row already exists with a conflicting value

### No audit rows appear

This usually means:

- you have not yet exercised both allow and deny scenarios
- you are connected to the wrong database
