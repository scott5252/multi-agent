# QA Guide For Specs 001 And 002

This document is the end-to-end QA guide for:

- `001-platform-foundation`
- `002-platform-auth-access`

It is written for both developers and non-developers. If you are comfortable with a terminal, use the `curl` and `pytest` steps. If you prefer a GUI client, you can use Postman or Insomnia anywhere this guide shows an HTTP request.

## What This Guide Covers

Spec `001` added the platform foundation:

- local setup and bootstrap flow
- database migrations and rollback validation
- API and worker startup
- operational endpoints: `/health/live`, `/health/ready`, `/version`, `/dependencies`
- tenant-scope primitives
- artifact and secret-provider abstractions
- repository quality gates and contract checks

Spec `002` added authentication and authorization:

- `AUTH_MODE=local_principal` for deterministic local testing
- `AUTH_MODE=auth0` for production-style authentication
- `/auth/me`
- `/auth/tenant-context/{tenant_id}`
- tenant user, tenant admin, and platform admin access boundaries
- platform-admin role-grant management
- support override request and approval flow
- access-decision auditing
- delegated credential and platform-secret boundary enforcement

## Prerequisites

- Python `3.12`
- `uv`
- Docker Desktop or Docker Engine with Compose v2
- A terminal
- Optional for the Auth0 section: an Auth0 tenant, API audience, and a valid access token

## Recommended Test Order

1. Complete setup and startup.
2. Run the Spec `001` checks.
3. Seed the Spec `002` test data.
4. Run the local-principal Spec `002` checks.
5. Run the automated validation commands.
6. Run the optional Auth0 validation.

## 1. Setup Overview

### 1.1 Install dependencies

From the repository root:

```bash
uv sync
```

### 1.2 Create local environment configuration

```bash
cp .env.example .env
```

Update `.env` so the local-principal catalog contains four test users:

- one tenant user
- one tenant admin
- two platform admins so the support-override flow can use a second approver

Use this exact value for `LOCAL_PRINCIPAL_CATALOG_JSON`:

```env
LOCAL_PRINCIPAL_CATALOG_JSON={"tenant-user-acme":{"catalog_key":"tenant-user-acme","display_name":"Tenant User","tenant_id":"11111111-1111-1111-1111-111111111111","org_id":"org-acme","role_codes":["tenant_user"],"permission_codes":["tenant:read"]},"tenant-admin-acme":{"catalog_key":"tenant-admin-acme","display_name":"Tenant Admin","tenant_id":"11111111-1111-1111-1111-111111111111","org_id":"org-acme","role_codes":["tenant_user","tenant_admin"],"permission_codes":["tenant:read","tenant:admin"]},"platform-admin-a":{"catalog_key":"platform-admin-a","display_name":"Platform Admin A","role_codes":["platform_admin"],"permission_codes":["tenant:admin","admin:role-grants:write","admin:support-overrides:write","admin:support-overrides:approve"]},"platform-admin-b":{"catalog_key":"platform-admin-b","display_name":"Platform Admin B","role_codes":["platform_admin"],"permission_codes":["tenant:admin","admin:role-grants:write","admin:support-overrides:write","admin:support-overrides:approve"]}}
```

Keep these other `.env` values as shown unless you intentionally want to test different providers:

- `APP_ENV=local`
- `AUTH_MODE=local_principal`
- `DATABASE_URL=postgresql+psycopg://postgres:postgres@127.0.0.1:5432/multi_agent_platform`
- `SECRET_PROVIDER=static`
- `STORAGE_PROVIDER=filesystem`

### 1.3 Start infrastructure

Start PostgreSQL:

```bash
docker compose up -d postgres
```

Optional: start MinIO if you also want to validate the local S3-compatible storage profile:

```bash
docker compose --profile storage up -d minio
```

### 1.4 Apply migrations

```bash
uv run alembic upgrade head
```

Expected result:

- the command completes without error
- the database contains the foundation and auth/access tables

### 1.5 Start the API

In terminal 1:

```bash
uv run uvicorn multi_agent_platform.api.main:app --reload
```

Expected result:

- the server starts on `http://127.0.0.1:8000`
- startup completes without configuration errors

### 1.6 Start the worker

In terminal 2:

```bash
uv run python -m multi_agent_platform.workers.main
```

Expected result:

- the worker starts without crashing
- no dependency or database errors are printed at startup

### 1.7 Define helper shell variables

In a third terminal, export these helpers for the rest of the guide:

```bash
export BASE_URL=http://127.0.0.1:8000
export TENANT_ID=11111111-1111-1111-1111-111111111111
export OTHER_TENANT_ID=22222222-2222-2222-2222-222222222222
```

Expected result:



Expected result:

- the upgrade succeeds
- `/health/ready` returns HTTP `200` again

## 3. Spec 002 Test Data Preparation

Complete this section once before running the Spec `002` manual checks.

### 3.1 Seed tenant rows

Create two tenants in PostgreSQL:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform <<'SQL'
INSERT INTO tenants (tenant_id, slug, display_name)
VALUES
  ('11111111-1111-1111-1111-111111111111', 'acme', 'Acme'),
  ('22222222-2222-2222-2222-222222222222', 'globex', 'Globex')
ON CONFLICT (slug) DO NOTHING;
SQL
```

Expected result:

- both tenants exist in the `tenants` table

### 3.2 Warm up persisted principal identities

Call `/auth/me` once for each local principal so the application persists the principal identity rows:

```bash
curl --silent -H "X-Local-Principal: tenant-user-acme" "$BASE_URL/auth/me" | uv run python -m json.tool
curl --silent -H "X-Local-Principal: tenant-admin-acme" "$BASE_URL/auth/me" | uv run python -m json.tool
curl --silent -H "X-Local-Principal: platform-admin-a" "$BASE_URL/auth/me" | uv run python -m json.tool
curl --silent -H "X-Local-Principal: platform-admin-b" "$BASE_URL/auth/me" | uv run python -m json.tool
```

Expected result:

- each request returns HTTP `200`
- each response shows the expected `auth_mode`, roles, permissions, and tenant context

### 3.3 Look up the persisted principal UUIDs

Run:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform -c \
"SELECT external_subject, principal_identity_id FROM principal_identities ORDER BY external_subject;"
```

Write down the `principal_identity_id` for `tenant-user-acme`. You will need it for the role-grant test below.

## 4. Spec 002 Manual Validation In Local-Principal Mode

### 4.1 Validate `/auth/me`

Tenant user:

```bash
curl -i -H "X-Local-Principal: tenant-user-acme" "$BASE_URL/auth/me"
```

Tenant admin:

```bash
curl -i -H "X-Local-Principal: tenant-admin-acme" "$BASE_URL/auth/me"
```

Platform admin:

```bash
curl -i -H "X-Local-Principal: platform-admin-a" "$BASE_URL/auth/me"
```

Expected result:

- all three requests return HTTP `200`
- each response contains `auth_mode: "local_principal"`
- tenant users and tenant admins show `tenant_id=$TENANT_ID`
- platform admins show no tenant-scoped identity by default

Negative test:

```bash
curl -i "$BASE_URL/auth/me"
```

Expected result:

- HTTP `401`
- the request is rejected because the local principal header is missing

### 4.2 Validate `/auth/tenant-context/{tenant_id}`

Same-tenant request:

```bash
curl -i \
  -H "X-Local-Principal: tenant-user-acme" \
  "$BASE_URL/auth/tenant-context/$TENANT_ID"
```

Cross-tenant request:

```bash
curl -i \
  -H "X-Local-Principal: tenant-user-acme" \
  "$BASE_URL/auth/tenant-context/$OTHER_TENANT_ID"
```

Expected result:

- same-tenant call returns HTTP `200`
- cross-tenant call returns HTTP `403`

This validates the core tenant isolation behavior added by Spec `002`.

### 4.3 Validate tenant user access boundaries

Try to use a tenant-admin endpoint as a tenant user:

```bash
curl -i \
  -H "X-Local-Principal: tenant-user-acme" \
  "$BASE_URL/admin/tenants/$TENANT_ID/role-grants"
```

Expected result:

- HTTP `403`
- tenant users cannot access tenant-admin-only surfaces

### 4.4 Validate platform-admin role-grant creation

Use `platform-admin-a` to create a tenant-scoped role grant for `tenant-user-acme`.

Replace `<TENANT_USER_PRINCIPAL_ID>` with the value you saved in section `3.3`.

```bash
curl -i \
  -X POST "$BASE_URL/admin/role-grants" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-a" \
  -d '{
    "principal_identity_id": "<TENANT_USER_PRINCIPAL_ID>",
    "scope_type": "tenant",
    "tenant_id": "11111111-1111-1111-1111-111111111111",
    "role_code": "tenant_user"
  }'
```

Expected result:

- HTTP `201`
- the response includes a new `role_grant_id`
- `status` is `active`

Negative test as an underprivileged caller:

```bash
curl -i \
  -X POST "$BASE_URL/admin/role-grants" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: tenant-admin-acme" \
  -d '{
    "principal_identity_id": "<TENANT_USER_PRINCIPAL_ID>",
    "scope_type": "tenant",
    "tenant_id": "11111111-1111-1111-1111-111111111111",
    "role_code": "tenant_user"
  }'
```

Expected result:

- HTTP `403`
- tenant admins cannot use this platform-admin-only role-grant route

### 4.5 Validate tenant-admin access to tenant role grants

Tenant admin reading their own tenant:

```bash
curl -i \
  -H "X-Local-Principal: tenant-admin-acme" \
  "$BASE_URL/admin/tenants/$TENANT_ID/role-grants"
```

Tenant admin attempting a different tenant:

```bash
curl -i \
  -H "X-Local-Principal: tenant-admin-acme" \
  "$BASE_URL/admin/tenants/$OTHER_TENANT_ID/role-grants"
```

Expected result:

- same-tenant request returns HTTP `200`
- the JSON array includes at least the grant you created in section `4.4`
- cross-tenant request returns HTTP `403`

### 4.6 Validate support override creation, approval, and use

First, confirm that a platform admin cannot read tenant-specific role grants without an approved override:

```bash
curl -i \
  -H "X-Local-Principal: platform-admin-a" \
  "$BASE_URL/admin/tenants/$TENANT_ID/role-grants"
```

Expected result:

- HTTP `403`

Create the override request:

```bash
curl -i \
  -X POST "$BASE_URL/admin/support-overrides" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-a" \
  -d '{
    "tenant_id": "11111111-1111-1111-1111-111111111111",
    "justification": "Investigate tenant-specific support issue",
    "idempotency_key": "qa002-override-1"
  }'
```

Copy the returned `support_override_request_id`.

Expected result:

- HTTP `201`
- the request status is `pending`

If you repeat this test, use a new `idempotency_key`.

Try to self-approve with the same admin:

```bash
curl -i \
  -X POST "$BASE_URL/admin/support-overrides/<SUPPORT_OVERRIDE_REQUEST_ID>/approve" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-a" \
  -d '{"expires_in_hours": 1}'
```

Expected result:

- HTTP `403`
- the requester cannot approve their own override

Approve with a second admin:

```bash
curl -i \
  -X POST "$BASE_URL/admin/support-overrides/<SUPPORT_OVERRIDE_REQUEST_ID>/approve" \
  -H "Content-Type: application/json" \
  -H "X-Local-Principal: platform-admin-b" \
  -d '{"expires_in_hours": 1}'
```

Expected result:

- HTTP `200`
- the request status is `approved`
- the response includes `approver_principal_id` and `expires_at`

Retry the tenant-specific read as `platform-admin-a`:

```bash
curl -i \
  -H "X-Local-Principal: platform-admin-a" \
  "$BASE_URL/admin/tenants/$TENANT_ID/role-grants"
```

Expected result:

- HTTP `200`
- the response succeeds only after the second approver completes approval

### 4.7 Validate access-decision auditing

After running the allow and deny tests above, inspect the audit tables:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform -c \
"SELECT decision, reason_code, surface_key, tenant_id, support_override_request_id, delegated_credential_link_id, secret_free, occurred_at FROM access_decision_records ORDER BY occurred_at DESC LIMIT 20;"
```

Optional: inspect the higher-level audit event log too:

```bash
docker compose exec -T postgres psql -U postgres -d multi_agent_platform -c \
"SELECT actor_id, action, entity_type, payload_redacted, occurred_at FROM audit_events ORDER BY occurred_at DESC LIMIT 20;"
```

Expected result:

- you can see both `allow` and `deny` decisions
- denied cross-tenant or admin-mismatch requests are recorded
- approved support-override access links to a `support_override_request_id`
- `secret_free` remains `true`
- no raw tokens, passwords, or API keys appear in the stored payloads

## 6. Optional Auth0 Validation

Run this section only if you have an Auth0 tenant and a valid access token.

### 6.1 Reconfigure for Auth0

Update `.env`:

- `AUTH_MODE=auth0`
- `AUTH0_DOMAIN=<your tenant>`
- `AUTH0_ISSUER=<your issuer>`
- `AUTH0_AUDIENCE=<your API audience>`

Restart the API after saving `.env`.

### 6.2 Validate missing-token rejection

```bash
curl -i "$BASE_URL/auth/me"
```

Expected result:

- HTTP `401`

### 6.3 Validate invalid-token rejection

```bash
curl -i \
  -H "Authorization: Bearer invalid-token" \
  "$BASE_URL/auth/me"
```

Expected result:

- HTTP `401`

### 6.4 Validate valid-token success

Set a valid token first:

```bash
export AUTH0_ACCESS_TOKEN="<paste valid token here>"
```

Then call:

```bash
curl -i \
  -H "Authorization: Bearer $AUTH0_ACCESS_TOKEN" \
  "$BASE_URL/auth/me"
```

Expected result:

- HTTP `200`
- the response shows `auth_mode: "auth0"`
- the resolved tenant context, permissions, and roles match the token and stored grants

```bash
uv run pytest tests/unit/config/test_auth_settings.py tests/unit/auth/test_jwt_validator.py tests/unit/auth/test_claims.py -q
```

This validates:

- Auth0 mode requires issuer, audience, and domain

## 8. Pass Criteria

The solution should be considered fully validated when all of the following are true:

- setup from a fresh checkout works without undocumented steps
- API and worker both start successfully
- `/health/live`, `/health/ready`, `/version`, and `/dependencies` behave as expected
- migration downgrade and recovery succeed
- tenant-scoped access is allowed only within the correct tenant
- tenant users, tenant admins, and platform admins are separated correctly
- platform-admin role grants work
- support overrides require justification and a second approver
- access decisions are auditable
- delegated credential and platform-secret boundaries pass their automated tests
- static analysis, tests, and coverage all pass

## 9. Troubleshooting

- `503 /health/ready`: verify PostgreSQL is running, migrations are at head, and the selected auth mode is configured correctly.
- `401 /auth/me` in local mode: verify the `X-Local-Principal` header is present and matches a catalog key in `.env`.
- `403` on tenant-admin routes: verify you used the correct tenant ID and principal role.
- `500` when creating support overrides or tenant-scoped role grants: confirm the target tenant row exists in the `tenants` table and the target principal identity has been created.
- No audit rows appear: make sure you exercised both allowed and denied protected routes after the API was started.
