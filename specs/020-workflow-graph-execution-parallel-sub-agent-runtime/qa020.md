# QA020: Workflow Graph Execution And Parallel Sub-Agent Runtime

## Goal

Validate that Spec 020 executes published workflow graphs through the runtime
worker. The checks cover bundle loading, tenant isolation, deterministic role
execution, parallel scout scheduling, join policy evaluation, checkpoint and
handoff evidence, side-effect intent summaries, manual resolution pauses,
redaction, worker integration, documentation, and automated quality evidence.

This guide is written for reviewers who want copy/paste commands and clear
expected results. It uses deterministic QA data and mock role execution only.
No command in this guide should call a real model provider, Google Calendar,
Gmail, weather, maps, Telegram Bot API, or any production host.

## What This Guide Covers

- Local QA environment setup in `multi_agent_platform_qa020`.
- Local-principal authentication for platform, Acme, and Globex users.
- Clean database reset with deterministic Acme and Globex tenants.
- Focused automated tests for graph planning and DB-backed execution.
- Worker execution of a claimed graph run from entry node to terminal node.
- Daily Intelligence Briefing fan-out with four scout branches in one wave.
- `all_success`, `quorum`, `first_success`, and `manual_resolution` join tests.
- Crash-resume behavior that skips already succeeded node steps.
- Cross-tenant published bundle denial.
- Redaction scans for secret-looking graph output and timeline fields.
- QA document validation, API validation, and Playwright smoke validation.
- Full quality gates required by the repository.

Current implementation note: Spec 020 adds graph orchestration and a
deterministic role-executor boundary. It does not add real skill connectors,
live provider credential resolution, Telegram natural-language aliases, or user
briefing preferences. Those are tracked by Specs 021 through 025.

## How To Use This Guide

Use two terminal windows from the repository root.

- Terminal A runs the API or worker when a command asks for a long-running
  process.
- Terminal B runs setup, focused tests, database checks, and quality commands.

Keep Terminal B open so shell variables and response files remain available.
Commands save reviewer evidence under `/tmp/qa020-*` when practical.

Important terms:

- A graph node is one role, join, approval, subworkflow, or terminal point.
- A run step is the durable row for one executed graph node.
- A wave is the scheduler's set of ready nodes for one pass.
- A branch result is the safe output summary consumed by a join.
- Manual resolution means the run is paused with durable approval evidence.
- Safe output means no raw secrets, prompts, model responses, or tool payloads.

## Troubleshooting

- If PostgreSQL commands fail, run `docker compose ps postgres` and confirm the
  service is healthy.
- If the API reads the wrong database, rerun the copy command for `.env.qa020`
  and restart the API.
- If focused tests pass but full coverage fails, inspect the coverage report
  for unrelated files before changing graph execution code.
- If Playwright validation cannot start processes, check `/tmp/qa020-api.log`
  and `/tmp/qa020-worker.log`.
- If a redaction check fails, search for raw values in run step output,
  timeline payloads, and side-effect intent summaries.
- If manual resolution does not pause, check the join policy's
  `failure_behavior` field.
- If a cross-tenant denial unexpectedly succeeds, inspect the run tenant id and
  workflow version bundle tenant id.
- If worker execution stalls, confirm the run status is `runnable` before the
  worker claims it.
